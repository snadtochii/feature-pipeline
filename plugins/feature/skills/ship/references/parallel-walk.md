# Ship — parallel walk (`--parallel` only)

Read this file at exactly one point: SETUP step 4, when `--parallel [N]` was passed. Without the flag this file is never read and ship's serial walk runs unchanged.

This reference changes **scheduling only**. Every PER TICKET hop from `SKILL.md` — the implementer brief content, the independent-reviewer spawn (Step 2, via `references/reviewer-prompt.md`), the address hop, the orchestrator's verification, the guardrails — applies to each worker verbatim; what changes is *when* tickets run (ready-set dispatch instead of one at a time), *where* the implementer works (an isolated git worktree — or, in a multi-repo workspace, whichever checkout its repo lane assigns per §1), and *who* writes shared state (only the orchestrator). END OF RUN and `--ui-test` are untouched: they run in the main checkout after the walk, exactly as the serial path prescribes.

## §1 Eligibility gate & graceful degradation

`--parallel` needs the project's worktree setup contract — the `worktree:` block in `claudedocs/tickets/config.yaml` (the `.worktreeinclude` file is part of the same contract but optional on its own: a missing file only makes the copy step a no-op). The contract's full definition lives in [`../../../docs/advanced.md`](../../../docs/advanced.md) §Worktree setup — consume it as written there; never restate or redefine it here or in a brief.

- **No `worktree:` block** → log one line — `--parallel needs the worktree setup contract (worktree: block in claudedocs/tickets/config.yaml); walking serially` — and run the serial walk. Not an error; the run proceeds.
- **`worktree.setup` fails or times out** for a ticket → log why (exit code + the last lines of output), then clean up the provisioning residue before anything else runs for that ticket: remove the worktree per §3's removal discipline (`--force` covers setup-generated leftovers like dependency dirs), and delete the pre-created ticket branch once confirmed still base-equivalent (`git rev-parse <branch>` equals `git rev-parse origin/<BASE_BRANCH>` — no worker ran, so it has no commits; in the unexpected diverged case, push the branch and let the serial walk reuse it instead of deleting). The delete matters: the branch survives worktree removal, and a leftover convention branch makes the serial path's branch creation fail. Then degrade: **drain** the workers already in flight (let them finish their hops; verify and merge each per §5), dispatch nothing new in parallel, and continue the remaining tickets **serially in the main checkout** per SKILL.md. One failed setup predicts the next — do not retry per ticket.
- **Solo run** → one ticket, nothing to parallelize; note it and run serially.

### Repo lanes (multi-repo workspaces)

When the run's tickets carry `repos:` frontmatter (a multi-repo workspace — the field's semantics are `skills/discover/references/multi-repo.md`), partition them into **lanes** — one lane per distinct repo named. A `repos:` value must resolve to an existing workspace child directory containing `.git`; a ticket naming a repo that doesn't resolve is **never dispatched** — log one note naming the unresolved value (a stale or mistyped `repos:` entry) and list the ticket in the end-of-run report under "needs serial resume" (fix the frontmatter, then resume). Each lane is an independent execution context: its own checkout, branches, and PRs. Lanes always run concurrently — cross-repo parallelism needs no worktrees.

- **Lane record — every orchestrator operation consumes it.** At partition time, bind per lane: the repo path (`<workspace>/<repo-dirname>`), its GitHub `owner/repo` (from that repo's `origin`), its `<BASE_BRANCH>`, and its execution site (§2). From then on **no orchestrator git/gh/test command runs against an ambient cwd**: the workspace root is not a git repo, so every `git` call is `git -C <lane-repo-path> …` and every `gh` PR call is repo-qualified (`gh pr view/edit/merge --repo <owner/repo> <n>`, or run from inside the lane's repo) — this covers SETUP's pre-flight (run its `git checkout <base> && git pull --ff-only` + clean-tree check **per lane repo**; the `gh auth status` check runs once), worker-hop verification, §5's merges and revalidation, END OF RUN (`--merge`, `--ui-test` — per resulting PR, in its lane's repo), and §7 recovery. Worktree provisioning and briefs already consume the record via §3/§4.

- **One lane** — a single-repo workspace (`repos:` never exists there) or a run whose tickets all name the same repo — means none of the lane rules apply: the walk runs exactly per the rest of this reference, unchanged. Lanes are a ≥2-lane concept.
- **A run with nothing to partition on is one lane** — ship's storage file §1 says when `repos:` exists at all; without it the walk runs unchanged.
- **Per-lane eligibility**: only a lane with ≥2 concurrent-eligible tickets needs the worktree contract. The two degradations above apply **per lane**: a worktree-needing lane in a repo without the contract logs one line — `lane <repo-dirname>: --parallel needs the worktree setup contract (worktree: block); walking this lane serially in its main checkout` — and walks serially in that repo's main checkout; a `worktree.setup` failure drains and degrades **within its lane only**. Other lanes are unaffected either way.
- **Epic runs never reach this subsection multi-lane** — SETUP's guard STOPs an epic whose children's `repos:` span repos (the integration branch cannot span repos); an epic that passes the guard is single-repo, one lane.
- The lane partition feeds §2 (execution site + exclusive dispatch), §3 (lane-keyed worktree paths), and §7 (per-repo recovery sweep). Everything else — briefs, hops, serialization ownership — is lane-independent.

## §2 Ready-set scheduling (greedy, no batch barriers)

Build the dependency graph over the run's tickets from their `blocked_by` metadata — read per ship's storage file §1. Dependencies outside the run were already confirmed terminal by SETUP's blocker check; dependencies **inside** the run were deferred to this scheduler by that check's `--parallel` exception — they are the graph's edges.

- A ticket is **ready** when every `blocked_by` dependency is **terminal** — `done`/`cancelled` before the run (ticket-resolution Step 6's canonical done clause), or merged-and-revalidated into the integration branch *during* the run (§5). This generalizes the state-transitions Status-query "next child" rule from next-single-child to all-deps-terminal. `partial-completion` is **not** terminal — it marks incomplete work resumable from a hint, not a delivered dependency; a dependent of a `partial-completion` blocker stays undispatched and is listed under "needs serial resume" (§6), exactly like a dependent of an in-run failure.
- **Terminal-for-dispatch is the orchestrator's judgment, not the blocker's frontmatter.** An in-run-merged blocker still reads `status: in-review` (finalizing to `done/` stays `sync`'s post-run job — never flip its status or run `/feature:sync` mid-run: a PR merged only into the integration branch is deliberately not promotable until the integration PR lands). But the dependent's inner `flow → build` re-runs ticket-resolution Step 6, whose done clause accepts only `done`/`cancelled` — so the dependent's brief **names each such blocker as satisfied** ("blocker `<ID>`: PR #`<n>` merged into `<BASE_BRANCH>` and revalidated — treat as done at the Step 6 blocker gate; its code is already in your fork point"), and that named override, not a status edit, is what keeps build from refusing. The override names only blockers merged-and-revalidated *in this run* — never a `partial-completion` one, which §2 keeps out of the ready set entirely.
- **Dispatch** every ready ticket through the selected runtime, up to **N in flight** (the `--parallel` cap; default 3), further capped by its Capacity operation. Reserve each worker’s stage and at least one leaf role before admitting it; print the effective cap and include the reservation in its runtime block. A ticket occupies a slot from its implementer spawn until its merge (or open-PR verification in a multi-solo run) completes — the reviewer and address hops included. The ready set is **global** across lanes, and N caps workers in flight globally — never per lane. Cross-repo `blocked_by` needs no new logic: a dependent stays undispatched until its blocker is terminal, regardless of lane.
- **Execution site (multi-lane runs only)**: lanes are classified **once, at SETUP, from the `blocked_by` graph** — the classification is fixed for the run and never re-evaluated against instantaneous in-flight counts (N-throttling can hold a lane to one worker at a time; that does not reclassify it). A **serial lane** — a single ticket, or a total `blocked_by` chain (no two tickets mutually unordered) — runs its tickets in that repo's **main checkout** via the serial mechanics, no worktree. A **worktree lane** — two or more concurrent-eligible (mutually unordered) tickets — provisions a worktree per dispatched ticket per §3, paths relative to that lane's repo, even while throttling happens to keep just one of its tickets in flight: that overhead buys a checkout that never flips mode mid-run, keeping the lane's main checkout on `<BASE_BRANCH>` — the premise §3's branch pre-creation and §5's merge step depend on. In a one-lane run this rule does not exist: dispatch provisions worktrees exactly as §3 prescribes.
- **Exclusive dispatch (multi-lane runs only)**: a ticket whose `repos:` names more than one repo is dispatched **barrier-and-drain** over the lanes it names. A ticket with **no** `repos:` in a multi-repo workspace has an unknown footprint, so it barriers **all** lanes in the run — log one note naming the missing field. Barrier-and-drain: the moment the exclusive ticket enters the ready set, **freeze** dispatch into every barriered lane (greedy refill of those lanes stops — this is what keeps the exclusive ticket from starving behind an ever-refilling lane), let their in-flight work drain, run the ticket serially in the main checkouts (today's behavior — no new cross-repo build mechanics), and resume greedy dispatch once it is terminal. No barriered lane dispatches concurrently while it is in flight; unbarriered lanes keep running.
- **Greedy**: whenever a ticket completes or fails (§6), recompute the ready set and dispatch newly-ready tickets immediately — never wait for a "wave" to finish.
- **Shapes**: an edge-free multi-solo run has every ticket ready at once (cap applies); a multi-solo run may also carry `blocked_by` edges between its own tickets — including cross-repo ones — via SETUP's `--parallel` blocker exception. A pure `blocked_by` chain has a ready set of one — the walk is effectively serial, one worktree at a time. An epic typically mixes both.
- A ticket whose dependency can never become terminal in this run — the dep is a declared-but-unwritten child, or itself failed (§6) — is **never dispatched**; list it in the end-of-run report under "needs serial resume", naming the blocking dependency.

Track the loop with TodoWrite (one item per ticket, annotated ready / in-flight / merged / failed / not-dispatched) and process worker completions as they arrive.

## §3 Worktree lifecycle (provision → work → remove)

The procedure itself lives in [`../../build/references/worktree.md`](../../build/references/worktree.md) — the shared lifecycle this walk and `build --worktree` both run. Consume it as written there; what follows is only this walk's bindings and the parallel-specific policy it supplies.

**When**: per dispatched ticket, before spawning its implementer — all from the main checkout. In a multi-lane run (§1 repo lanes) this runs only for lanes provisioning worktrees.

**Input bindings** (worktree.md §0) — every one is lane-keyed in a multi-lane run, so `<wt-path>` is a sibling of the **lane's repo** and the branch is cut from that repo's `origin/<BASE_BRANCH>`:

| worktree.md §0 input | Bound to |
|---|---|
| `<TICKET-ID>` | the dispatched ticket |
| `<repo-root>` | the lane's repo path from §1's lane record (single-lane run: the one repo) |
| `<BASE_BRANCH>` | the lane's base — SETUP step 3's bound base, i.e. the integration branch on an epic run |
| `<branch>` | `skills/build/references/pr-creation.md` §2's convention |
| `<ticket-folder>` | the absolute main-checkout ticket folder the worker's brief carries (§4) |
| setup-failure policy | **§1 degradation** — clean up the residue, drain in-flight workers, walk the rest of the lane serially |
| removal trigger | after the ticket's PR is merged and revalidated (§5), or — for a failed ticket — after its branch is confirmed **pushed** (§6) |

**Branch pre-creation is the premise this walk depends on.** worktree.md §2 step 2 creates `<branch>` at `git worktree add` time precisely because `<BASE_BRANCH>` must stay checked out in the lane's main checkout — §5's merge step reads that checkout, and git refuses one branch in two worktrees. The worker therefore **reuses** the provisioned branch; §4's workdir brief and `pr-creation.md` §1's provisioned-branch short-circuit are what hold it to that. Crash-resume (a branch that survived a §7 prune) is worktree.md §2 step 2's re-attach shape.

**Removal discipline** is worktree.md §4: its safety predicate (work committed on `<branch>`, or the branch pushed) gates `git worktree remove` + `git worktree prune`, and `--force` covers setup-generated leftovers like dependency directories, never unpushed commits. This walk supplies only the trigger, above.

**Config marker**: worktree.md §2 step 6 handles the walk-up check, the conditional copy, and the storage-mode requirements on the resolved file. A worktree whose copy fails those requirements aborts that ticket's dispatch with the `.worktreeinclude` remedy; a merely-absent `config.yaml` is copied rather than treated as the failure.

## §4 Worker briefs — worktree + explicit base-branch injection

Each worker gets the PER TICKET Step 1 implementer brief from SKILL.md, plus these parallel-specific additions:

- **Workdir**: "Work in `<wt-path>` — an isolated git worktree already on branch `<branch>`, cut from `origin/<BASE_BRANCH>`. Reuse that branch: commit on it directly; do not create, switch, or fork branches, and never `git checkout <BASE_BRANCH>` (it is checked out in another worktree; git will refuse)." This matches the **provisioned-branch short-circuit** that opens the branch-decision matrix in `skills/build/references/pr-creation.md` §1: with a worktree provisioned, build's PR step reuses the checked-out branch and skips every matrix row — it must never stash-and-checkout `<BASE_BRANCH>` to fork fresh (that row's checkout is exactly what git refuses here) and never re-create the convention branch (it exists; this worktree is on it). The brief states it explicitly so the worker does not have to infer it.
- **Base branch, named twice**: "Your fork point is `origin/<BASE_BRANCH>` (already done); your PR must target `<BASE_BRANCH>` — after `flow --pr` opens the PR, check `gh pr view <n> --json baseRefName` and retarget with `gh pr edit <n> --base <BASE_BRANCH>` if it differs." **Never repoint `origin/HEAD`** — not the orchestrator, not a worker: `refs/remotes/origin/HEAD` is repo-level state shared by every worktree of the clone, so a repoint aimed at one worker poisons base detection for every concurrent sibling.
- **Ticket argument**: the brief's ticket identity and Step 1's `Skill feature:flow` ticket argument are the `<TICKET_ARG_BLOCK>` resolved per ship's storage file §3 — an absolute main-checkout path or a bare ID, as that section states for the detected mode — never a form resolved relative to the worker's cwd. Stage artifacts land per-ticket, so concurrent workers never collide.
- **State is orchestrator-owned**: the `<STATE_CLAUSE_BLOCK>` resolved per ship's storage file §3, followed by: "Return lesson candidates — atomic one-subject lines per the lessons-log contract — in your final report instead. This overrides, by name, the state steps the skills you invoke prescribe: plan/build's start-of-run Transition 1, build's verdict-gate Transition 5, and build's verdict-gate lessons capture — skip each; the orchestrator applies them at its serialization points (§5)."

Group three of these additions — the **Workdir**, the **Base branch, named twice**, and the **State is orchestrator-owned** clause — in the worker's brief under a `## Stage overrides` heading; flow copies that section verbatim into its plan and build stage briefs ([`../../flow/references/stage-briefs.md`](../../flow/references/stage-briefs.md) §7), so they reach the stages unparaphrased. The **Ticket argument** bullet stays outside the heading: it addresses the worker's own `Skill feature:flow` invocation, and flow resolves the stages' ticket argument itself.

The Step 2 reviewer hop is read-only (`gh` + file reads) and spawns exactly as in the serial walk. The Step 3 address hop edits code, so its brief carries the same workdir addition — it works in the ticket's worktree, where the PR branch is checked out, and ship's wrapper (re-run typecheck + the spec's verification tests) runs there too. Its brief also **overrides SKILL.md Step 3's epic-run merge clause by name**: the worker stops after address + push + that wrapper — it never runs `gh pr merge`; the merge belongs to the orchestrator's serialized queue (§5), which fires only after this verification.

In a multi-lane run the workdir and base-branch injections above are **per-lane**: `<wt-path>`, `<branch>`, and `<BASE_BRANCH>` all belong to the lane's repo. The ticket argument stays **workspace-level** (ship's storage file §3) — it belongs to no lane.

Consumer note: listing `claudedocs/tickets/config.yaml` in `.worktreeinclude` is the cheapest way to carry the project's `validate:` config — and its storage-mode marker — into each worktree of a single-repo workspace, where `<wt-path>` sits outside the repo that holds the file. Without the entry, §3's provisioning copies it anyway (worktree.md §2 step 6), and the storage-mode requirements on the resolved file still gate dispatch. In a multi-repo workspace neither is needed: `config.yaml` sits above the repo root, out of reach of a repo-relative `.worktreeinclude` pattern, but the worktrees sit **under the workspace root** (`<wt-path>` is a sibling of the lane's repo), so the validation hook's ancestor walk-up finds the workspace `config.yaml` on its own and per-edit validation keeps firing in every lane's worktrees.

## §5 Serialization points (the orchestrator, one at a time)

Parallel workers produce **code**; every shared mutation is orchestrator-only — **across all lanes**: in a multi-lane run the transitions, folder moves, status writes, merge queue, and lessons writes below stay with the one orchestrator, so workspace-level state has exactly one writer regardless of lane count (the merge queue stays globally one-at-a-time; lanes add no merge parallelism). Each transition below dispatches through its procedure in [`state-transitions-fs.md`](../../flow/references/state-transitions-fs.md) / [`state-transitions-server.md`](../../flow/references/state-transitions-server.md) for the detected storage mode, in the forms ship's storage file §6 states:

- **Transition 1, once, up front.** Epic run: fire T1 for the epic (form per ship's storage file §6) before any dispatch, then set each child's status to `in-progress` at its dispatch. Multi-solo run: fire T1 per ticket at its dispatch. T1 is idempotent, but under parallelism only the orchestrator invokes it — workers never do.
- **All state transitions** happen in the orchestrator between dispatches: after verifying a worker's PR is open and correctly based, apply Transition 5 (status `in-review` on the ticket; for an epic child also T5's epic-level effect — form per ship's storage file §6). Finalization to `done` remains `sync`'s job, exactly as in the serial walk.
- **Integration merges (epic run): one at a time, revalidated per merge.** When a ticket's three hops are done: `gh pr merge <n> --squash --delete-branch` from the main checkout (the local branch is still checked out in the ticket's worktree, so the local delete no-ops with a warning — the §3 worktree removal clears it), then `git checkout <integration branch> && git pull --ff-only` in the main checkout, then re-run typecheck + the test suite against the now-current integration head **before the next merge** — ship's END-OF-RUN staleness rule for multi-solo `--merge`, applied per merge: two independent PRs can interact through shared behavior with no textual conflict. Merge conflicts and red revalidations are resolved in the main checkout during this serialized step (or treated as that ticket's failure, §6) — never inside a worktree. Only after green does the merge count as terminal for §2's ready set.
- **Lessons store**: collect every worker's candidate entries and apply the lessons-log write contract ([`lessons-log-fs.md`](../../flow/references/lessons-log-fs.md) / [`lessons-log-server.md`](../../flow/references/lessons-log-server.md) §4–§5: supersession scan, merge-in-place, prefer-newest) serially, one candidate at a time, at the end of the run — the store and its write operations per ship's storage file §2.

Multi-solo runs have no in-run merges — the resulting PRs stay open, and `--merge` at END OF RUN already serializes them with per-merge revalidation.

## §6 Worker failure isolation

A worker that ends `partial`/`stuck` (or errors out) sinks **its ticket, not the run**:

- Siblings in flight run to completion; the ready set keeps advancing for every ticket that does not depend on the failed one.
- The failed ticket keeps its state: apply Transition 4 (`status: partial-completion` — form per ship's storage file §6) and record the worker's reported stuck-point as the continuation hint in the run report; artifacts already written stay on the ticket.
- **Push, then remove**: confirm the ticket's branch is pushed — `git -C "<wt-path>" push -u origin <branch>` if the worker didn't get that far — then remove the worktree per §3. The branch holds the resumable code state; the worktree holds nothing.
- Dependents of the failed ticket are never dispatched (§2) and are listed alongside it.
- The end-of-run report lists **per-ticket outcomes** — merged / PR open / failed (with its continuation hint) / not dispatched (with its blocking dep) — and names exactly which tickets **need serial resume** (`/feature:ship <id>` once the blocker is resolved, or `/feature:flow`/`/feature:build` for finer control).

A genuine run-level blocker — branch protection on the integration branch, a red revalidation that can't be fixed — still STOPs the run per SKILL.md's guardrails, after draining in-flight workers and reporting each ticket's state.

## §7 Recovery (crash or kill mid-parallel-run)

Everything needed to resume lives on disk and on GitHub; the worktrees are the only parallel-specific residue.

1. `git worktree list` — run it in **every repo whose tickets were in the run** (one repo in a single-lane run; each lane's repo in a multi-lane run): every `<repo-dirname>-worktrees/<TICKET-ID>` path is a ticket that was in flight in that repo.
2. Triage each such ticket: PR merged — `gh pr view --json state,mergeCommit` plus the merge predicate's reachability check (`skills/build/references/pr-creation.md`: `git merge-base --is-ancestor <merge-sha> origin/<BASE_BRANCH>`), aimed at this run's `<BASE_BRANCH>` — the integration branch for an epic child, not `<base>` (a child's merge reaches `<base>` only when the integration PR lands) → only cleanup remains; PR open → the review/address hops may be incomplete, and SKILL.md's Recovery idempotency scan applies unchanged; branch pushed but no PR → the implementer died mid-hop, resume from PR creation; commits only in the worktree → push them (`git -C "<wt-path>" push -u origin <branch>`) or discard deliberately.
3. Reconcile ticket state against that evidence per ship's storage file §5 (the orchestrator owns status, so a crash can leave a merged PR at a stale `in-review` — `/feature:sync` fixes those).
4. **Prune**: once each branch is pushed or discarded, run the cleanup in `../../build/references/worktree.md` §5 — `git worktree remove` each stale path, then `git worktree prune`.
5. Re-run ship — with `--parallel` to resume the concurrent walk over the remaining tickets, or without it to finish serially. SETUP reuses the existing integration branch either way.
