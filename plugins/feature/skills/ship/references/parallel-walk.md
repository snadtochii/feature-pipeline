# Ship — parallel walk (`--parallel` only)

Read this file at exactly one point: SETUP step 4, when `--parallel [N]` was passed. Without the flag this file is never read and ship's serial walk runs as `SKILL.md` states.

This reference changes **scheduling only**. Every PER TICKET hop from `SKILL.md` — the implementer brief content, the independent-reviewer spawn (Step 2, via `references/reviewer-prompt.md`), the address hop, the orchestrator's verification, the guardrails — applies to each worker verbatim; what changes is *when* tickets run (ready-set dispatch instead of one at a time) and *where* the implementer works (an isolated git worktree — or, in a multi-repo workspace, whichever checkout its repo lane assigns per §1). Ticket state, failure isolation and the run report stay as [`SKILL.md`](../SKILL.md) states them for every run. END OF RUN and its end-of-run UI pass run after the walk, one pass at a time, exactly as the serial path prescribes; each of their git and gh calls takes the lane record of the repository it acts on ([`SKILL.md`](../SKILL.md) SETUP step 1), and each UI pass runs in the lane of the repository it tests with the `test.repos` entry selected for that repository ([`ui-verification.md`](ui-verification.md) step 0).

## §1 Eligibility gate & graceful degradation

`--parallel` needs the project's worktree setup contract — the `worktree:` block in `claudedocs/tickets/config.yaml` (the `.worktreeinclude` file is part of the same contract but optional on its own: a missing file only makes the copy step a no-op). The contract's full definition lives in [`../../../docs/advanced.md`](../../../docs/advanced.md) §Worktree setup — consume it as written there; never restate or redefine it here or in a brief.

- **No `worktree:` block** → log one line — `--parallel needs the worktree setup contract (worktree: block in claudedocs/tickets/config.yaml); walking serially` — and run the serial walk. Not an error; the run proceeds.
- **`worktree.setup` fails or times out** for a ticket → log why (exit code + the last lines of output), then clean up the provisioning residue before anything else runs for that ticket: remove the worktree per §3's removal discipline (`--force` covers setup-generated leftovers like dependency dirs), and delete the pre-created ticket branch once confirmed still base-equivalent (`git -C "<repo-path>" rev-parse <branch>` equals `git -C "<repo-path>" rev-parse origin/<BASE_BRANCH>` — no worker ran, so it has no commits; in the unexpected diverged case, push the branch and let the serial walk reuse it instead of deleting). The delete matters: the branch survives worktree removal, and a leftover convention branch makes the serial path's branch creation fail. Then degrade: **drain** the workers already in flight (let them finish their hops; verify and merge each per §5), dispatch nothing new in parallel, and continue the remaining tickets **serially in the main checkout** per SKILL.md. One failed setup predicts the next — do not retry per ticket.
- **Solo run** → one ticket, nothing to parallelize; note it and run serially.

### Repo lanes (multi-repo workspaces)

When the run's tickets carry `repos:` frontmatter (a multi-repo workspace — the field's semantics are `skills/discover/references/multi-repo.md`), partition them into **lanes** — one lane per distinct repo named. A `repos:` value must pass the lane binding in ship's storage file §1, resolving to an existing workspace child directory containing `.git`; a ticket naming a repo that doesn't resolve was already skipped by [`SKILL.md`](../SKILL.md) SETUP step 1. Each lane is an independent execution context: its own checkout, branches, and PRs. Lanes run concurrently, up to N — cross-repo parallelism needs no worktrees.

- **Lane record — every orchestrator operation consumes it.** [`SKILL.md`](../SKILL.md) SETUP step 1 defines the record and its command forms, and binds it on every run. This walk's uses of it are worker-hop verification, §5's merges and revalidation, END OF RUN (`--merge` and the UI pass — per resulting PR, in its lane's repo, and each UI pass in the lane of the repository it tests), and §7 recovery. Worktree provisioning and briefs consume the record via §3/§4.

- **One lane** — a single-repo workspace (`repos:` never exists there) or a run whose tickets all name the same repo — means none of the partition rules apply: the walk runs exactly per the rest of this reference, unchanged. The partition rules are a ≥2-lane concept.
- **A run with nothing to partition on is one lane** — ship's storage file §1 says when `repos:` exists at all; without it the walk runs unchanged.
- **Per-lane eligibility**: only a lane with ≥2 concurrent-eligible tickets needs the worktree contract. The two degradations above apply **per lane**: a worktree-needing lane in a repo without the contract logs one line — `lane <repo-dirname>: --parallel needs the worktree setup contract (worktree: block); walking this lane serially in its main checkout` — and walks serially in that repo's main checkout; a `worktree.setup` failure drains and degrades **within its lane only**. Other lanes are unaffected either way.
- **Epic runs never reach this subsection multi-lane** — SETUP step 1's guard STOPs, on every run, an epic whose children's `repos:` span repos (the integration branch cannot span repos); an epic that passes the guard is single-repo, one lane.
- The lane partition feeds §2 (execution site), §3 (lane-keyed worktree paths), and §7 (per-repo recovery sweep). Everything else — briefs, hops, serialization ownership — is lane-independent.

## §2 Ready-set scheduling (greedy, no batch barriers)

Build the dependency graph over the run's tickets from their `blocked_by` metadata — read per ship's storage file §1. Dependencies outside the run were already confirmed met by SETUP's blocker check; dependencies **inside** the run are the graph's edges.

- A ticket is **ready** when every `blocked_by` dependency is **met** — `done`/`cancelled` before the run (ticket-resolution Step 6's canonical done clause), merged-and-revalidated into the integration branch *during* the run (§5), or, across lanes, ready as [`SKILL.md`](../SKILL.md) Readiness defines it. This generalizes the state-transitions Status-query "next child" rule from next-single-child to all-deps-met. `partial-completion` is **not** met — it marks incomplete work resumable from a hint, not a delivered dependency, and SETUP step 1 skips such a ticket with its dependents.
- **Met-for-dispatch is the orchestrator's judgment, not the blocker's frontmatter.** An in-run-merged blocker still reads `status: in-review` (finalizing to `done/` stays `sync`'s post-run job — never flip its status or run `/feature:sync` mid-run: a PR merged only into the integration branch is deliberately not promotable until the integration PR lands). The dependent's inner `flow → build` re-runs ticket-resolution Step 6, whose merged-sibling clause accepts a same-repo sibling on its own — its merge commit is in the worker's checkout, cut from `<BASE_BRANCH>` after the merge. A cross-repo blocker is passed by the line [`SKILL.md`](../SKILL.md) Readiness defines.
- **Dispatch** every ready ticket through the selected runtime, up to **N in flight** (the `--parallel` cap; default 3), further capped by its Capacity operation. Reserve each worker’s stage and at least one leaf role before admitting it; print the effective cap and include the reservation in its runtime block. A ticket occupies a slot from its implementer spawn until its merge (or open-PR verification in a multi-solo run) completes — the reviewer and address hops included. The ready set is **global** across lanes, and N caps workers in flight globally — never per lane. A dependent stays undispatched until its edges are met, regardless of lane.
- **Execution site (multi-lane runs only)**: lanes are classified **once, at SETUP, from the `blocked_by` graph** — the classification is fixed for the run and never re-evaluated against instantaneous in-flight counts (N-throttling can hold a lane to one worker at a time; that does not reclassify it). A **serial lane** — a single ticket, or a total `blocked_by` chain (no two tickets mutually unordered) — runs its tickets in that repo's **main checkout** via the serial mechanics, no worktree. A **worktree lane** — two or more concurrent-eligible (mutually unordered) tickets — provisions a worktree per dispatched ticket per §3, paths relative to that lane's repo, even while throttling happens to keep just one of its tickets in flight: that overhead buys a checkout that never flips mode mid-run, keeping the lane's main checkout on `<BASE_BRANCH>` — the premise §3's branch pre-creation and §5's merge step depend on. In a one-lane run this rule does not exist: dispatch provisions worktrees exactly as §3 prescribes.
- **Greedy**: whenever a ticket completes or fails (§6), recompute the ready set and dispatch newly-ready tickets immediately — never wait for a "wave" to finish.
- **Shapes**: an edge-free multi-solo run has every ticket ready at once (cap applies); a multi-solo run may also carry cross-repo `blocked_by` edges between its own tickets. A pure `blocked_by` chain has a ready set of one — the walk is effectively serial, one worktree at a time. An epic typically mixes both.
- A ticket whose dependency can never be met in this run — the dep is a declared-but-unwritten child, or itself failed (§6) — is **never dispatched**: it is skipped per [`SKILL.md`](../SKILL.md) SETUP step 1 or Failure isolation, naming the blocking dependency.

Track the loop with TodoWrite (one item per ticket, annotated ready / in-flight / merged / failed / skipped) and process worker completions as they arrive.

## §3 Worktree lifecycle (provision → work → remove)

The procedure itself lives in [`../../build/references/worktree.md`](../../build/references/worktree.md) — the shared lifecycle this walk and `build --worktree` both run. Consume it as written there; what follows is only this walk's bindings and the parallel-specific policy it supplies.

**When**: per dispatched ticket, before spawning its implementer — all from the main checkout. In a multi-lane run (§1 repo lanes) this runs only for lanes provisioning worktrees.

**Input bindings** (worktree.md §0) — every one is lane-keyed in a multi-lane run, so `<wt-path>` is a sibling of the **lane's repo** and the branch is cut from that repo's `origin/<BASE_BRANCH>`:

| worktree.md §0 input | Bound to |
|---|---|
| `<TICKET-ID>` | the dispatched ticket |
| `<repo-root>` | the lane's repo path from §1's lane record (single-lane run: the one repo) |
| `<BASE_BRANCH>` | the lane's base — SETUP step 3's bound base, i.e. the integration branch on an epic run |
| `<branch>` | `skills/build/references/pr-creation.md` §2's convention |
| `<ticket-folder>` | the absolute main-checkout ticket folder the worker's brief carries (§4) |
| setup-failure policy | **§1 degradation** — clean up the residue, drain in-flight workers, walk the rest of the lane serially |
| removal trigger | after the ticket's PR is merged and revalidated (§5), or — for a failed ticket — after its branch is confirmed **pushed** (§6) |

**Branch pre-creation is the premise this walk depends on.** worktree.md §2 step 2 creates `<branch>` at `git worktree add` time precisely because `<BASE_BRANCH>` must stay checked out in the lane's main checkout — §5's merge step reads that checkout, and git refuses one branch in two worktrees. The worker therefore **reuses** the provisioned branch; §4's workdir brief and `pr-creation.md` §1's provisioned-branch short-circuit are what hold it to that. Crash-resume (a branch that survived a §7 prune) is worktree.md §2 step 2's re-attach shape.

**Removal discipline** is worktree.md §4: its safety predicate (work committed on `<branch>`, or the branch pushed) gates `git worktree remove` + `git worktree prune`, and `--force` covers setup-generated leftovers like dependency directories, never unpushed commits. This walk supplies only the trigger, above.

**Config marker**: worktree.md §2 step 6 handles the walk-up check, the conditional copy, and the storage-mode requirements on the resolved file. A worktree whose copy fails those requirements aborts that ticket's dispatch with the `.worktreeinclude` remedy; a merely-absent `config.yaml` is copied rather than treated as the failure.

## §4 Worker briefs — worktree + explicit base-branch injection

Each worker gets the PER TICKET Step 1 implementer brief from SKILL.md, plus these parallel-specific additions:

- **Workdir**: "Work in `<wt-path>` — an isolated git worktree already on branch `<branch>`, cut from `origin/<BASE_BRANCH>`. Reuse that branch: commit on it directly; do not create, switch, or fork branches, and never `git checkout <BASE_BRANCH>` (it is checked out in another worktree; git will refuse)." This matches the **provisioned-branch short-circuit** that opens the branch-decision matrix in `skills/build/references/pr-creation.md` §1: with a worktree provisioned, build's PR step reuses the checked-out branch and skips every matrix row — it must never stash-and-checkout `<BASE_BRANCH>` to fork fresh (that row's checkout is exactly what git refuses here) and never re-create the convention branch (it exists; this worktree is on it). The brief states it explicitly so the worker does not have to infer it.
- **Base branch, named twice**: "Your fork point is `origin/<BASE_BRANCH>` (already done); your PR must target `<BASE_BRANCH>` — after `flow --pr` opens the PR, check `gh pr view <n> --repo "<owner/repo>" --json baseRefName` and retarget with `gh pr edit <n> --repo "<owner/repo>" --base <BASE_BRANCH>` if it differs." **Never repoint `origin/HEAD`** — not the orchestrator, not a worker: `refs/remotes/origin/HEAD` is repo-level state shared by every worktree of the clone, so a repoint aimed at one worker poisons base detection for every concurrent sibling.
- **Ticket argument**: the brief's ticket identity and Step 1's `Skill feature:flow` ticket argument are the `<TICKET_ARG_BLOCK>` resolved per ship's storage file §3 — an absolute main-checkout path or a bare ID, as that section states for the detected mode — never a form resolved relative to the worker's cwd. Stage artifacts land per-ticket, so concurrent workers never collide.
- **UI testing stays off**: the worker's Step 1 invocation carries `--no-ui-testing` whatever its test entries declare — an entry has one `test.url` and browser passes never boot concurrently, so concurrent workers cannot each run one. Tickets a `--parallel` run walks serially take the flag from [`driver-decision.md`](driver-decision.md) §1.
- **State is orchestrator-owned**: as [`SKILL.md`](../SKILL.md) State ownership states for every run, in the brief's state clause. This walk only fixes when those writes land (§5).

The worker's `## Stage overrides` section is the one [`SKILL.md`](../SKILL.md) PER TICKET defines, with the **Workdir** added and the **Base branch, named twice** wording in place of its base-branch bullet; flow copies that section verbatim into every stage brief — plan, implement, review and close ([`../../flow/references/stage-briefs.md`](../../flow/references/stage-briefs.md) §7), so they reach the stages unparaphrased. The **Ticket argument** and **UI testing stays off** bullets stay outside the heading: they address the worker's own `Skill feature:flow` invocation, and flow resolves the stages' ticket argument and flags itself.

The Step 2 reviewer hop is read-only (`gh` + file reads) and spawns exactly as in the serial walk. The Step 3 address hop edits code, so its brief carries the same workdir addition — it works in the ticket's worktree, where the PR branch is checked out, and the orchestrator's Hop verification after this hop runs its local fallback, when the PR reports no checks, there too (`cd "<wt-path>"`). Its brief also **overrides SKILL.md Step 3's epic-run merge clause by name**: the worker stops after address + push — it never runs `gh pr merge`; the merge belongs to the orchestrator's serialized queue (§5), which fires only after Hop verification is green.

In a multi-lane run the workdir and base-branch injections above are **per-lane**: `<wt-path>`, `<branch>`, and `<BASE_BRANCH>` all belong to the lane's repo. The ticket argument stays **workspace-level** (ship's storage file §3) — it belongs to no lane.

Consumer note: listing `claudedocs/tickets/config.yaml` in `.worktreeinclude` is the cheapest way to carry the project's storage-mode marker — and its `test:`, `git:` and `worktree:` config — into each worktree of a single-repo workspace, where `<wt-path>` sits outside the repo that holds the file. Without the entry, §3's provisioning copies it anyway (worktree.md §2 step 6), and the storage-mode requirements on the resolved file still gate dispatch. In a multi-repo workspace neither is needed: `config.yaml` sits above the repo root, out of reach of a repo-relative `.worktreeinclude` pattern, but the worktrees sit **under the workspace root** (`<wt-path>` is a sibling of the lane's repo), so worktree.md §2 step 6's ancestor walk-up finds the workspace `config.yaml` on its own in every lane's worktrees.

## §5 Serialization points (the orchestrator, one at a time)

Parallel workers produce **code**; every shared mutation is orchestrator-only — **across all lanes**: in a multi-lane run the transitions, folder moves, status writes, merge queue, and lessons writes stay with the one orchestrator, so workspace-level state has exactly one writer regardless of lane count (the merge queue stays globally one-at-a-time; lanes add no merge parallelism). State writes land between dispatches, per [`SKILL.md`](../SKILL.md) State ownership and in the forms ship's storage file §6 states: an epic's Transition 1 before any dispatch, each child's or multi-solo ticket's at its own dispatch.

- **Integration merges (epic run): one at a time, revalidated per merge.** When a ticket's three hops are done: `(cd "<repo-path>" && gh pr merge <n> --squash --delete-branch)` from the main checkout (the local branch is still checked out in the ticket's worktree, so the local delete no-ops with a warning — the §3 worktree removal clears it), then `git -C "<repo-path>" checkout <integration branch> && git -C "<repo-path>" pull --ff-only` in the main checkout, then, in a `(cd "<repo-path>" && …)` subshell, re-run typecheck + the test suite against the now-current integration head **before the next merge** — ship's END-OF-RUN staleness rule for multi-solo `--merge`, applied per merge: two independent PRs can interact through shared behavior with no textual conflict. Merge conflicts and red revalidations are resolved in the main checkout during this serialized step (or treated as that ticket's failure, §6) — never inside a worktree. Only after green does the merge count as met for §2's ready set.

Multi-solo runs have no in-run merges — the resulting PRs stay open, and `--merge` at END OF RUN already serializes them with per-merge revalidation.

## §6 Worker failure isolation

[`SKILL.md`](../SKILL.md) Failure isolation governs a failed ticket on every run, and its Run report the outcome lines. This walk adds:

- **Siblings in flight run to completion**, and the ready set keeps advancing for every ticket that does not depend on the failed one.
- **Push, then remove**: confirm the ticket's branch is pushed — `git -C "<wt-path>" push -u origin <branch>` if the worker didn't get that far — then remove the worktree per §3. The branch holds the resumable code state; the worktree holds nothing.
- **Drain before a stop**: a lane stop or a run stop, as Failure isolation names them, first drains the in-flight workers it affects, then reports each ticket's state. A red revalidation that can't be fixed is a merged integration head that is red.

## §7 Recovery (crash or kill mid-parallel-run)

Everything needed to resume lives on disk and on GitHub; the worktrees are the only parallel-specific residue.

1. `git -C "<repo-path>" worktree list` — run it in **every repo whose tickets were in the run** (one repo in a single-lane run; each lane's repo in a multi-lane run): every `<repo-dirname>-worktrees/<TICKET-ID>` path is a ticket that was in flight in that repo.
2. Triage each such ticket: PR merged — `gh pr view "<branch>" --repo "<owner/repo>" --json state,mergeCommit` plus the merge predicate's reachability check (`skills/build/references/pr-creation.md`: `git -C "<repo-path>" merge-base --is-ancestor <merge-sha> origin/<BASE_BRANCH>`), aimed at this run's `<BASE_BRANCH>` — the integration branch for an epic child, not `<base>` (a child's merge reaches `<base>` only when the integration PR lands) → only cleanup remains; PR open → the review/address hops may be incomplete, and SKILL.md's Recovery idempotency scan applies unchanged; branch pushed but no PR → the implementer died mid-hop, resume from PR creation; commits only in the worktree → push them (`git -C "<wt-path>" push -u origin <branch>`) or discard deliberately.
3. Reconcile ticket state against that evidence per ship's storage file §5, its pending Transition 5 rule included (the orchestrator owns status, so a crash can leave a merged PR at a stale `in-review` — `/feature:sync` fixes those).
4. **Prune**: once each branch is pushed or discarded, run the cleanup in `../../build/references/worktree.md` §5 — `git -C "<repo-path>" worktree remove` each stale path, then `git -C "<repo-path>" worktree prune`.
5. Re-run ship — with `--parallel` to resume the concurrent walk over the remaining tickets, or without it to finish serially. SETUP reuses the existing integration branch either way.
