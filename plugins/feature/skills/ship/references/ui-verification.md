# Ship — end-of-run UI verification (`--ui-test` only)

Read this file only when `--ui-test` was passed (default is no browser pass). The pass runs **after** the resulting PR(s) are open (END OF RUN in ship's SKILL.md) and **before** any `--merge` — the evidence has to land on an existing PR, and on a `--merge` run it's what the human still gets. Besides the PR evidence, it rewrites each covered ticket's `05-tests.md` with the result and gives its `06-summary.md` a `## UI verification` section (step 4), so the ticket store — not only a PR comment — records what the browser verified. It never changes a ticket's verdict, its state or status, or the PR outcome; a setup gap (posted on the PR as *not verified*), a behavioral failure or a layout finding is reported and the run continues to its normal open/merge ending.

**Supported `--ui-test` contract (what "evidence on the PR" means).** The per-AC **verdict** and the required-check findings always reach the PR. **Screenshots** reach it *inline* only where they are hostable — i.e. where the consumer versions the ticket folder (step 3, Tracked); where the consumer gitignores `claudedocs/` (Ignored) they are referenced by their run-local path. Path-only degradation is a **documented, supported outcome, not a broken promise** — inline visual evidence deliberately requires the ticket folder to be versioned. Universal inline embedding regardless of `.gitignore` (uploading each shot as a Release/gist asset and embedding the asset URL) is **not part of this contract** — do not improvise it; every "post the screenshots" phrasing below resolves to this contract.

The assembled branch is the first point the whole UI story is testable, and the orchestrator runs in main context where browser MCP is reachable. Spawn **one** `ui-tester` subagent per run (one browser session, not per ticket) to run the acceptance criteria plus the required UI checks against the assembled branch, then post its UI-test evidence (the verdict and findings plus the screenshots — inline when the ticket folder is tracked, else a path manifest; see step 3) to the resulting PR:
- **Epic run** → assembled branch is `integration/<epic-id>`; the evidence posts to the integration PR.
- **Solo run** → assembled branch is the ticket's open PR head; the evidence posts to that PR.
- **Multi-solo run** → the one end-of-run pass walks each ticket's open PR head in turn, posting each ticket's evidence to its own PR. Each ticket is a distinct branch and app-state, so the single session re-runs the pre-flight per ticket — re-check-out that ticket's branch (`git checkout <ticket-branch> && git pull --ff-only`) and, if `test.start` booted the app, re-boot it (with its own §4 teardown) — before that ticket's checks and screenshot post.

1. **Pre-flight (reuse, do not reinvent).** Resolve the app URL + auth as [`test-preflight.md`](../../close-stage/references/test-preflight.md) prescribes — §1 URL resolution from the project `test:` block (`test.url` → CLAUDE.md hint → dev-port probe, held as a data value), §2 reachability `curl`, §3 optional `test.start` boot + bounded poll with §4 teardown, §5 auth recipe (`storage_state` → `attach_tab`) composed into the spawn prompt. That reference is the single source of truth for the recipe — don't restate it here, with **one ship-specific substitution**: §3 materializes the launch script with the `Write` tool, which ship's orchestrator doesn't carry (it has Bash but no Write — see step 3). Materialize the **same fixed-path script** (`/tmp/fp-test-preflight-<id>.sh`, entire body = the `test.start` value) with a **single-quoted heredoc whose delimiter is a verified-unique nonce** — confirm the nonce line does not occur in the `test.start` value before writing — the same mechanism step 3 uses for comment bodies. A single-quoted heredoc performs no expansion, so quotes / `$()` / backticks in the declared command land as file content, preserving §3's no-shell-reparse guarantee; everything else in §3 (fixed path, PID capture, bounded poll, §4 teardown) applies unchanged. §3's PID/script files are keyed on a stable id: use `<epic-id>` for the epic pass (whose assembled branch is `integration/<epic-id>`, not one ticket) and the ticket-id for the solo/multi-solo passes. Check out the assembled branch first (`git checkout <assembled-branch> && git pull --ff-only`) so the running app reflects the code under test.

   **The orchestrator provisions no environment.** It resolves the URL and boots only a declared `test.start`, per `test-preflight.md`. It never builds images, starts compose projects, creates schemas, seeds data or picks a second port. A project whose app needs an isolated stack declares that stack as its `test.start`, and the `test.start_timeout` ceiling bounds its boot.

   **Serves the PR head or not verified.** The resolved URL counts as serving the checked-out assembled branch only when §3 booted `test.start` during this pass, for this ticket (multi-solo) or this epic, after the checkout. When §2 finds the URL already reachable on its first probe, nothing establishes that it serves the PR head — [`test-preflight.md`](../../close-stage/references/test-preflight.md) §3's fixed-port hazard — so that URL is a setup gap: go to step 5 before any spawn. Never boot a second instance and never switch ports to work around it. On a multi-solo run the rule applies per ticket, so a later ticket whose URL is still answered by an earlier ticket's server degrades too.
2. **Spawn.** Give the `ui-tester` subagent (subagent_type `feature:ui-tester`) a self-contained brief: the acceptance criteria to verify behaviorally — the `<AC_SOURCE_BLOCK>` resolved per ship's storage file §3 — the pre-flight-resolved reachable URL, the §5 auth recipe, the absolute evidence home ship's storage file §7 resolves (on a multi-solo run, one evidence home per ticket, keyed by ticket ID), and the verbatim contents of [`../../build/references/ui-checks.md`](../../build/references/ui-checks.md) under a `## Required UI checks (use this exactly)` header — the same contract the close stage's test checkpoint injects. The tester captures each acceptance criterion and each required state at both widths, into that evidence home.

   How the brief labels the criteria depends on the run shape, so the report maps back to each ticket for step 4:
   - **Solo run** — plain `AC <n>`, numbered as the spec numbers them.
   - **Epic run** — every criterion labelled `<CHILD-ID> AC <n>`, drawn from the children on the roster ship's storage file §1 resolves that were merged into `integration/<epic-id>`; a child not merged there is not in the brief.
   - **Multi-solo run** — one report section per ticket ID, each with that ticket's own criteria, findings and verdict.

   It judges **behavior** (flow completes, elements respond, no console errors, right text renders) **and** layout against the findings list in `ui-checks.md` §4, so overflow and layout shift come back as findings. Aesthetics — the observations `ui-checks.md` §4 names — stay with the human, judged from the images.
3. **Post the evidence to the resulting PR**, following [`../../review/references/pr-comments.md`](../../review/references/pr-comments.md) §7 injection discipline. `gh pr comment --body-file` posts **text only** — it can't reproduce the web UI's paste-to-upload (that hits GitHub's private `user-attachments` asset endpoint, which `gh`/the public API doesn't expose), so it can only reference an **already-hosted** URL. Whether the screenshots are hostable is decided per ship's storage file §7, which selects one of the two outcomes below:
   - **Tracked** (the consumer versions the ticket folder) → the screenshots are committed and pushed with the assembled branch, so they're hostable. Commit them — staging only the evidence home (`git add -- "<evidence-home>"`), never a broad `git add` that could sweep the browser's default output directory — (subject `<id>: ui-test screenshots`), push to the assembled branch, capture the pushed commit SHA, and **embed each inline** — the acceptance-criterion screenshots and the error, empty and disabled state screenshots alike — by **commit-SHA** raw URL — `https://github.com/<OWNER>/<REPO>/blob/<pushed-sha>/<path>?raw=true` (SHA, never the branch name, so the link survives the `--merge` `--delete-branch`). Real visual evidence on the PR.
   - **Ignored** (e.g. a plugin repo that gitignores `claudedocs/`) → the screenshots stay local run artifacts; there's nothing to host, so post the per-AC verdict and the findings plus a **manifest of their file paths** — acceptance-criterion and state screenshots alike — (never claim they're attached). This is the supported path-only outcome (above), not a gap — a consumer that wants inline screenshots on the PR versions its ticket folder, or waits for the deferred Release-asset upgrade.

   Either way the orchestrator has Bash but no Write tool, so materialize the comment body the way the reviewer hop does — a §5 quoted-heredoc into a `mktemp -d` file with a verified-unique nonce delimiter — then post with `gh pr comment "<N>" --body-file "<file>"`: `<N>` a controlled integer, `<OWNER>`/`<REPO>`/`<pushed-sha>` command-substitution values, never a `--body "…"` literal, never interpolating agent-generated text or file paths into the command, never `eval`. The verdict always reaches the PR; the images reach it inline wherever the ticket folder is versioned, and degrade to an honest path manifest where it isn't — never dropped, never overclaimed as embedded.
4. **Write the result back to the tickets.** Runs only when the tester actually ran and returned a report. Hold each ticket's parsed result from the moment the tester returns, and write after the last ticket's step-3 evidence post and before any `--merge`, so every ticket's location is settled when its artifacts are written. The covered tickets:
   - **Solo run** — the ticket, from the whole report.
   - **Multi-solo run** — each ticket whose pass ran, from its own report section; a ticket whose pre-flight degraded is not written.
   - **Epic run** — each child in the brief, from the criteria carrying its `<CHILD-ID>` label, renumbered to `AC <n>`. A failed required UI check tied to no child criterion — the implicit `UI states (required check)` criterion of [`ui-checks.md`](../../build/references/ui-checks.md) §5, such as a shared overflow — goes under `## Failed Criteria` in every covered child's file, marked epic-wide, so each of those children records `partial`; a non-failing note tied to no criterion goes under `## Observations` in every covered child's file, marked epic-wide. No epic-level tests artifact is written.

   Perform each ticket's writes per ship's storage file §8 — `05-tests.md` first, then the `## UI verification` section of `06-summary.md`. Failing criteria are recorded as failing, exactly as the PR comment reports them; the write never alters the ticket's verdict, its state or status, or the PR outcome.
5. **Degrade, never block.** A setup gap is any of: the app unreachable with no `test.start`; a `test.start` that timed out (its §4 teardown runs first); no `test:` config or no resolvable URL; a reachable URL not shown to serve the PR head (step 1); the browser MCP unavailable (detected before any boot). On a setup gap the orchestrator **posts one *not verified* comment** to that ticket's PR — the integration PR on an epic run — naming the reason, the resolved URL (or "none"), the head SHA (`git rev-parse HEAD` of the checked-out assembled branch), and what would make the pass verifiable: declare `test.url`, and `test.start` for a branch-specific app. It posts exactly as step 3 does — a nonce heredoc into a `mktemp -d` file, then `gh pr comment "<N>" --body-file "<file>"` — with `<N>` a controlled integer and the SHA a command-substitution value; neither the URL nor any agent text is interpolated into the command. The pass then records the gap in the run report and returns for that ticket or epic, and the run continues to the normal end-of-run PR outcome; a failed *not verified* post is reported, never fatal. A tester that crashed or timed out is not a setup gap: it is reported in the run report only, and a failed screenshot post still posts the verdict and findings text. A degraded pass — any setup gap, or a tester that crashed or timed out — writes no artifact, so each ticket keeps the skip body its close stage wrote; a failed step-4 write is reported, naming the ticket and the artifact, and the run continues. Mirrors the test-checkpoint's non-blocking skip in [`test-preflight.md`](../../close-stage/references/test-preflight.md) §6 — a UI-test setup gap, a failed behavioral check or a layout finding is recorded, never fatal, and never blocks or alters the resulting-PR outcome.
