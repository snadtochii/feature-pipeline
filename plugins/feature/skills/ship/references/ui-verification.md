# Ship — end-of-run UI verification

Read this file at END OF RUN in ship's SKILL.md, unless `--no-ui-testing` was passed — then this file is never read and no browser pass runs. The pass runs **after** the resulting PR(s) are open and **before** any `--merge` — the evidence has to land on an existing PR, and on a `--merge` run it's what the human still gets. Besides the PR evidence, it rewrites each covered ticket's `05-tests.md` with the result and gives its `06-summary.md` a `## UI verification` section (step 4), so the ticket store — not only a PR comment — records what the browser verified. It never changes a ticket's verdict, its state or status, or the PR outcome; a ticket whose plan carries no UI signal is skipped with a run-report line (step 0), and a setup gap (posted on the PR as *not verified*), a behavioral failure or a layout finding is reported and the run continues to its normal open/merge ending.

**Supported evidence contract (what "evidence on the PR" means).** The per-AC **verdict** and the required-check findings always reach the PR. **Screenshots** reach it *inline* only when the project opted into attaching ([`../../build/references/ui-attach.md`](../../build/references/ui-attach.md) §1), in two cases: `gh` can attach — `gh pr comment --attach` uploads them to GitHub's attachment storage, whether or not the ticket folder is versioned (step 3, Attached) — or, failing that, the consumer versions the ticket folder (step 3, Tracked). Otherwise (Ignored) they are referenced by their run-local path: captures from a logged-in session leave the machine only for a project that opted into publishing them. Path-only degradation is a **documented, supported outcome, not a broken promise**. Hosting anywhere else — release assets, gists, a direct call to the attachment endpoint — is **not part of this contract** — do not improvise it; every "post the screenshots" phrasing below resolves to this contract.

The assembled branch is the first point the whole UI story is testable, and the orchestrator runs in main context, where browser MCP is reachable and a declared browser driver can run. The pass is made of **passes** — one per selected test entry per covered ticket (step 0), each with its own pre-flight, one `ui-tester` subagent and its own teardown, run one at a time and never concurrently ([`test-preflight.md`](../../close-stage/references/test-preflight.md) Entry selection, sequential passes). Each covered ticket's UI-test evidence (the verdict and findings plus the screenshots — attached, embedded from the tracked ticket folder, or listed as a path manifest; see step 3) is posted to its resulting PR:
- **Epic run** → assembled branch is `integration/<epic-id>`; the evidence posts to the integration PR.
- **Solo run** → assembled branch is the ticket's open PR head; the evidence posts to that PR.
- **Multi-solo run** → the tickets in run order, and within a ticket its passes in `repos:` order; each ticket's evidence posts to its own PR. Each ticket is a distinct branch and app state, so every pass runs its own pre-flight — it checks out that ticket's branch (step 1) and, when the entry's `start` booted the app, re-boots it, with its own §4 teardown, before that pass's checks. A ticket's step-3 post — its Tracked commit and push included — and any step-5 head-SHA read finish before the next ticket's first checkout, so each ticket's evidence lands on its own branch.

**Repository binding.** No command of the pass runs against an ambient working directory — in a multi-repo workspace the project root is not a git repository. Every git call is `git -C "<path>" …` and every PR post is `gh pr comment --repo "<owner/repo>" "<N>" …`, the discipline [`parallel-walk.md`](parallel-walk.md) §1's lane record sets for a lane run, applied here to every run shape. `<owner/repo>` and `<N>` are parsed from the URL of the PR the run already holds — the ticket's PR from its hops, or the integration PR ship opened — so they are controlled values, never agent text — every `gh` call of the pass takes them from that URL, whichever repository the pass tests. Under `--parallel`, a pass's repository path for its git calls comes from the lane record of the repository it tests. In a single-repo workspace the repository path is the project root, and nothing else changes.

0. **Select — per covered ticket, before any pre-flight.** The covered tickets are the run's tickets whose PR is open at this point; on an epic run, the children merged into `integration/<epic-id>`. A ticket whose run ended at a blocker with no open PR is not covered. For each covered ticket:
   1. **UI signal.** Run the close stage's skip-detection scan ([`close-stage/SKILL.md`](../../close-stage/SKILL.md) §1 step a, the only copy of its keyword list) over the ticket's `02-plan.md`, located per ship's storage file §9. Take the list with a one-line `Grep` of that file for its `Skip-detection scan` line, never a full read of the skill. The scan is a match test: where the plan is a file, a case-insensitive `Grep` of it that returns only whether it matched, never a full read, and every covered ticket's scan goes out as parallel calls in one message.
   2. **Entry selection** — only for a ticket with a UI signal, so a run with none never reads `test-preflight.md`. Apply [`test-preflight.md`](../../close-stage/references/test-preflight.md) Entry selection to the ticket's `repos:` as ship's storage file §1 binds it and to the `test:` block of the `config.yaml` copy ship loaded at SETUP's **Storage mode.** step. It yields no entry, one, or several in `repos:` order. Ship writes none of the close stage's skip artifacts; it records each outcome as this reference says.
   3. **Outcome.**
      - No UI signal → no pass, no PR comment and no write-back for the ticket; one run-report line, `UI verification <id>: skipped — no UI signal in 02-plan.md`.
      - A UI signal, and Entry selection ended in its no testable repo case (row 1 with zero matches, or row 3) → a setup gap (step 5) naming that row's cause: no `test.repos` entry for the ticket's repositories (row 1), or a ticket that declares no `repos:` with no flat block to fall back to (row 3).
      - Otherwise → one pass per selected entry. A `repos:` value whose key Entry selection's key validation rejected is never booted, and the run report names it.
   4. **Epic run.** The epic's passes are the union of its covered children's selected entries, in roster order and then each child's `repos:` order, one pass per distinct entry. The pass for an entry briefs only the children whose own selection includes it; a child with no UI signal is in no brief and is not written back. A child with no `repos:` selects through Entry selection's rows 2–4. A child's setup gap posts to the integration PR.

1. **Pre-flight, per pass (reuse, do not reinvent).** Resolve the app URL + auth for the pass's entry as [`test-preflight.md`](../../close-stage/references/test-preflight.md) prescribes — §1 URL resolution from the entry (`test.url` → CLAUDE.md hint → dev-port probe, held as a data value), §2 reachability `curl`, §3 optional `test.start` boot + bounded poll with §4 teardown, §5 auth recipe (`storage_state` → `attach_tab`) composed into the spawn prompt. That reference is the single source of truth for the recipe — don't restate it here, with **one ship-specific substitution**: §3 materializes the launch script with the `Write` tool, which ship's orchestrator doesn't carry (it has Bash but no Write — see step 3). Materialize the **same fixed-path script** (`/tmp/fp-test-preflight-<pass-key>.sh`, entire body = the `test.start` value) with a **single-quoted heredoc whose delimiter is a verified-unique nonce** — confirm the nonce line does not occur in the `test.start` value before writing — the same mechanism step 3 uses for comment bodies. A single-quoted heredoc performs no expansion, so quotes / `$()` / backticks in the declared command land as file content, preserving §3's no-shell-reparse guarantee; everything else in §3 (fixed path, PID capture, bounded poll, §4 teardown) applies unchanged.

   **Pass key.** Entry selection's `<pass-key>`, with ship's stable id in place of `<ticket-id>` (that subsection's substitution clause): `<id>-<repo>` for a `test.repos` pass and `<id>` for a flat-block or no-entry pass. `<id>` is `<epic-id>` for an epic pass, whose assembled branch is `integration/<epic-id>` rather than one ticket's, and the ticket ID otherwise.

   **Repository and checkout.** Before the boot, bind the pass to its repository and check out the assembled branch, so the running app reflects the code under test:
   - **Repository path** — `<project-root>/<repo>` for a `test.repos` pass, `<project-root>` for a flat-block or no-entry pass; under `--parallel`, the lane record's repo path for that repository.
   - **Branch present** — `git -C "<repo-path>" ls-remote --exit-code --heads origin "<assembled-branch>"`. A non-zero exit is a setup gap (step 5) and nothing is booted: the repository does not carry the assembled branch, and its base-branch code is never tested as the PR head.
   - **Checkout** — when `git -C "<repo-path>" worktree list --porcelain` shows `<assembled-branch>` checked out in a linked worktree, at a path other than `<repo-path>` itself (a `--parallel` worktree still holding its ticket's branch), run `git -C "<wt-path>" pull --ff-only` and treat the pass as worktree-bound under test-preflight.md's [Launch directory](../../close-stage/references/test-preflight.md#launch-directory-and-path-base) rule, so `start` runs from `<wt-path>`. Otherwise — the branch held by `<repo-path>`'s own tree included — run `git -C "<repo-path>" checkout "<assembled-branch>" && git -C "<repo-path>" pull --ff-only` as one call. The branch-present check and the worktree listing are independent and go out as parallel calls in one message. A failed checkout or pull is a setup gap (step 5).

   `auth.storage_state` still resolves against the main checkout (test-preflight.md §5). The same model-read of `claudedocs/tickets/config.yaml` that yields the `test:` block binds `attach` per [`ui-attach.md`](../../build/references/ui-attach.md) §1: on when `git.attach_screenshots` is `true` or `--attach-screenshots` was passed, off otherwise.

   **The orchestrator provisions no environment.** It resolves the URL and boots only a declared `test.start`, per `test-preflight.md`. It never builds images, starts compose projects, creates schemas, seeds data or picks a second port. A project whose app needs an isolated stack declares that stack as its `test.start`, and the `test.start_timeout` ceiling bounds its boot.

   **Serves the PR head or not verified.** The resolved URL counts as serving the checked-out assembled branch only when §3 booted the entry's `start` during this pass, after this pass's checkout. When §2 finds the URL already reachable on its first probe, nothing establishes that it serves the PR head — [`test-preflight.md`](../../close-stage/references/test-preflight.md) §3's fixed-port hazard — so that URL is a setup gap: go to step 5 before any spawn. Never boot a second instance and never switch ports to work around it. The rule applies per pass, so a later pass whose URL is still answered by an earlier pass's server degrades too, and Entry selection's duplicate-URL guard applies across all of the run's passes. Each pass's §4 teardown finishes before the next pass's checkout.

   **Driver pass.** A pass whose entry declares `driver` runs [`test-preflight.md` Browser driver](../../close-stage/references/test-preflight.md#browser-driver) — its driver lifecycle and driver teardown — in place of §3's boot, §4's teardown and §5's recipe, after this step's checkout. Ship's substitutions:
   - **Pass directory** — `<pass-dir>` keeps the pre-flight's path, keyed by this pass's pass key.
   - **Entry file** — `<pass-dir>/entry.json` is materialized with a single-quoted heredoc whose delimiter is a verified-unique nonce, confirmed absent from every line of the JSON body. Values are JSON-escaped in the body, so the `test.start` value reaches the driver as file content only.
   - **Session file** — written with `printf '%s\n' '<id>' > '<pass-dir>/session'`, and only after the id matches `^[a-f0-9]{12}$`.
   - **No launch script** — a driver pass writes no `/tmp/fp-test-preflight-<pass-key>.sh`.
   - **Serves the PR head** — §2 answering on its first probe is the step 5 gap, raised before `doctor` or `launch`, so no browser starts. A `launch` reporting `server: already-running` gets the driver teardown, then the same gap; only `server: booted` after this pass's checkout serves the PR head. A `launch` exit 1 beginning `app unreachable` is step 5's unreachable or timed-out gap.
   - **Driver unavailable** — every driver-unavailable result of the lifecycle is a step 5 gap. Ship writes none of the close stage's skip artifacts.
   - **Teardown** — the driver teardown takes §4's place and finishes before the next pass's checkout, even when the pass errored.
   - **Tab attach** — an entry that also sets `auth.attach_tab` gets one run-report line, the close stage's notice: `<test.auth.attach_tab | test.repos.<repo>.auth.attach_tab> is ignored under driver: browser-cli — the driver has no tab attach.` Nothing about it enters the brief.
   - **Prior captures** — on a solo or multi-solo run whose ticket was a driver ticket (ship's SKILL.md SETUP step 2), its per-ticket close stage already captured into this pass's evidence home, and its `05-tests.md` lists those files. Before the spawn, move them aside in one call over the absolute, `'`-free evidence home — `mkdir '<pass-dir>/prior' && find '<evidence-home>' -maxdepth 1 -type f -name '*.png' -exec mv -- {} '<pass-dir>/prior/' \;` — so step 3's set and step 4's listing carry this pass's captures only. The filter is the `*.png` that step 4's listing reads, never a copy of the capture names [`ui-checks.md`](../../build/references/ui-checks.md) §3 fixes. A tester that returns a report leaves them to the driver teardown, which removes `<pass-dir>`. A tester that crashed or timed out gets them moved back before the teardown — `find '<pass-dir>/prior' -maxdepth 1 -type f -exec mv -f -- {} '<evidence-home>/' \;` — so the `05-tests.md` the ticket keeps (step 5) still lists files that exist.
2. **Spawn — one `ui-tester` per pass.** Give each pass's `ui-tester` subagent (subagent_type `feature:ui-tester`) a self-contained brief: the acceptance criteria to verify behaviorally — the `<AC_SOURCE_BLOCK>` resolved per ship's storage file §3 — that pass's pre-flight-resolved reachable URL, that pass's §5 auth recipe, the absolute evidence home ship's storage file §7 resolves (one per ticket on a multi-solo run, and the pass's per-repo home when its ticket or epic has two or more passes), and the verbatim contents of [`../../build/references/ui-checks.md`](../../build/references/ui-checks.md) under a `## Required UI checks (use this exactly)` header — the same contract the close stage's test checkpoint injects. When the pass's ticket or epic has two or more passes, the brief also carries the close stage's scoping sentence: `Repository under test: <repo>. Verify only the acceptance criteria observable in this application; report every other criterion as not applicable in <repo>, never as failed.` The tester captures each acceptance criterion and each required state once per viewport, at both widths, into that evidence home, and names the viewport of every failure.

   **Driver pass brief.** A driver pass's brief carries `Auth recipe: carried by the driver session` in place of the §5 recipe, then this paragraph verbatim — the close stage's driver Auth paragraph ([`close-stage/SKILL.md`](../../close-stage/SKILL.md) §1 step b):

   > **Auth — the driver session carries it.** The pre-flight imported any declared auth.storage_state into the session at launch; do not load or save a storage state, and do not attach to a tab. If the app shows a login wall, report the criteria behind it as not verified (unauthenticated session) — never script credential entry.

   and then the composed [driver block](../../close-stage/references/test-preflight.md#driver-block), every placeholder concrete and absolute, its `drive` timeout written in the runtime's own form ([`runtime-claude.md`](../../flow/references/runtime-claude.md) / [`runtime-codex.md`](../../flow/references/runtime-codex.md) §Tool results). The `ui-checks.md` injection is the same as on any other pass.

   How the brief labels the criteria depends on the run shape, so the report maps back to each ticket for step 4:
   - **Solo or multi-solo pass** — plain `AC <n>`, numbered as the ticket's spec numbers them; a pass covers one ticket.
   - **Epic pass** — every criterion labelled `<CHILD-ID> AC <n>`, drawn only from the children this pass briefs (step 0); a child not merged into `integration/<epic-id>` is in no brief.

   It judges **behavior** (flow completes, elements respond, no console errors, right text renders) **and** layout against the findings list in `ui-checks.md` §4, so overflow and layout shift come back as findings. Aesthetics — the observations `ui-checks.md` §4 names — stay with the human, judged from the images.

   A ticket or epic with two or more passes merges their results per criterion under the close stage's [Multi-pass results](../../close-stage/references/test-preflight.md#multi-pass-results) rules.
3. **Post the evidence to the resulting PR** — one post per PR, after the last pass that covers it and, on a multi-solo run, before the next ticket's first checkout — following [`../../review/references/pr-comments.md`](../../review/references/pr-comments.md) §7 injection discipline. The screenshots take the first outcome below that applies; with `attach` off, the post takes the Ignored outcome and carries no marker:
   - **Attached** — only when `attach` is on (step 1) and the evidence home holds a capture [`ui-attach.md`](../../build/references/ui-attach.md) §3 recognizes. Run that reference **before any upload**: §8's dedupe read of the PR for its evidence markers — `<!-- feature:ui-evidence <id> -->` and any part marker (`<id>` the ticket ID; the epic ID for the integration-PR post), with `--repo "<owner/repo>"` on its `gh pr view`, and on a solo or multi-solo run its `--jq` filter reduced to the comments term, `.comments[] | select(.author.login == env.GH_LOGIN) | .body`, in every §8 read this step makes: a marker in that PR's body is its per-ticket build's own evidence post, not this pass's — §2's probe against `gh pr comment` and §3's size listing go out as parallel calls in one message — the probe only on the run's first post, its result reused for every later PR of a multi-solo run. Its main marker found → post nothing for this PR, parts included, and record `already posted`; otherwise §3's **GitHub set** (per child, children in ticket order, on an epic's integration-PR post; per ticket on a multi-solo run; per repository in pass order where per-repo homes exist, §3's per-repo rule), joined with each failed criterion's `**Viewport**` — and, with per-repo homes, its `**Repo**` — from the tester's report, §4 alt text and path gate, and §5's attach-variant section after the verdict and findings, with one `Full capture set:` line per covered ticket. Post with `gh pr comment --repo "<owner/repo>" "<N>" --body-file "<file>"` plus one `--attach` argument per batch-1 capture, built per §6; a set over 50 posts each later batch as a §6 **Batches** part comment, its body materialized like the comment's and posted with the same `--repo`, once this run's own comment has landed, and a failed part is reconciled per that reference's §7. A failed probe, gate or selection, or a refused attach, falls through to the outcome ship's storage file §7 selects below — one retry, and only after §8's dedupe read confirms the failed attach posted nothing (a comment that landed with some uploads stands as §7's partial outcome) — and §7's outcome line records why.
   - **Tracked** (only when `attach` is on, as the fallback below Attached, and ship's storage file §7 finds the evidence home versioned by the checkout the pass tested) → the screenshots are committed and pushed with the assembled branch, so they're hostable. Commit them in that checkout with `git -C "<project-root>"` — staging only the evidence home (`git -C "<project-root>" add -- "<evidence-home>"`), never a broad `git add` that could sweep the browser's default output directory — (subject `<id>: ui-test screenshots`), push to the assembled branch, capture the pushed commit SHA (`git -C "<project-root>" rev-parse HEAD`), and **embed inline** the [`ui-attach.md`](../../build/references/ui-attach.md) §3 **GitHub set**, in its order, by **commit-SHA** raw URL — `https://github.com/<OWNER>/<REPO>/blob/<pushed-sha>/<path>?raw=true` (SHA, never the branch name, so the link survives the `--merge` `--delete-branch`) — plus one `Full capture set:` line per covered ticket. The commit carries the whole evidence home; the post embeds only the set. Real visual evidence on the PR.
   - **Ignored** (`attach` off, or e.g. a plugin repo that gitignores `claudedocs/`) → the screenshots stay local run artifacts; nothing is hosted, so post the per-AC verdict and the findings plus [`ui-attach.md`](../../build/references/ui-attach.md) §5's **manifest** over the §3 GitHub set, with its `Full capture set:` line(s) (never claim they're attached). This is the supported path-only outcome (above), not a gap — a consumer that wants inline screenshots on the PR enables attaching.

   With `attach` on, a Tracked or Ignored post carries the same marker as an attached one, so a re-run's dedupe read finds whichever posted. Record one line per PR in the run report — `UI evidence <id>: ` followed by the [`ui-attach.md`](../../build/references/ui-attach.md) §7 outcome (`attached <n>`, `attached <k> (partial: <reason>)`, `tracked`, `manifest (<reason>)` or `already posted`), plus its upgrade hint when the probe failed.

   Whichever outcome applies, the orchestrator has Bash but no Write tool, so materialize the comment body the way the reviewer hop does — a §5 quoted-heredoc into a `mktemp -d` file with a verified-unique nonce delimiter — then post with `gh pr comment --repo "<owner/repo>" "<N>" --body-file "<file>"` (plus the Attached outcome's `--attach` arguments): `<N>` a controlled integer and `<owner/repo>` a controlled value, both parsed from the PR URL the run holds, `<OWNER>`/`<REPO>`/`<pushed-sha>` command-substitution values, never a `--body "…"` literal, never interpolating agent-generated text or file paths into the command, never `eval`. The verdict always reaches the PR; with attaching enabled the images reach it inline — uploaded, or embedded from a versioned ticket folder — and they degrade to an honest path manifest otherwise — never dropped, never overclaimed as embedded.
4. **Write the result back to the tickets.** A ticket is written when at least one of its passes ran a tester that returned a report. Hold each ticket's parsed result from the moment its tester returns, and write after the last ticket's step-3 evidence post and before any `--merge`, so every ticket's location is settled when its artifacts are written. The covered tickets:
   - **Solo run** — the ticket, from its passes' reports.
   - **Multi-solo run** — each ticket with a pass that ran, from its own passes' reports.
   - **Epic run** — each child in a pass's brief, from the criteria carrying its `<CHILD-ID>` label across the passes that briefed it, renumbered to `AC <n>`. A failed required UI check tied to no child criterion — the implicit `UI states (required check)` criterion of [`ui-checks.md`](../../build/references/ui-checks.md) §5, such as a shared overflow — goes under `## Failed Criteria` in the file of every child that pass briefed, marked epic-wide, so each of those children records `partial`; a non-failing note tied to no criterion goes under `## Observations` in the same files, marked epic-wide. No epic-level tests artifact is written.

   Perform each ticket's writes per ship's storage file §8 — `05-tests.md` first, including its `## Screenshots` section composed as that section prescribes, then the `## UI verification` section of `06-summary.md`, whose `- screenshots: <n> captures, listed in 05-tests.md` bullet carries the total that section lists. A ticket tested in two or more passes takes that section's multi-pass form, in which a degraded pass of a ticket that is written records its reason in its own `## Pass: <repo>` section. Failing criteria are recorded as failing, exactly as the PR comment reports them; the write never alters the ticket's verdict, its state or status, or the PR outcome.
5. **Degrade, never block.** A setup gap is any of: a UI-signalled ticket with no selected entry (step 0); the assembled branch absent from the pass's repository, or a failed checkout or pull (step 1); the app unreachable with no `test.start`; a `test.start` that timed out (its §4 teardown runs first); no resolvable URL; a URL Entry selection's duplicate-URL guard rejects; a reachable URL not shown to serve the PR head (step 1); for an entry without `driver`, the browser MCP unavailable (detected once, before the run's first boot); for a driver entry, the browser driver unavailable — `node '<driver>' doctor` failing (checked per pass, or SETUP's driver probe already failed), a `launch` error other than `app unreachable`, a failed session check, an unrecognized `driver` value, or an unusable home directory or evidence home. On a setup gap the orchestrator **posts one *not verified* comment per degraded pass** — one per ticket for a no-entry gap — to that ticket's PR, the integration PR on an epic run. The comment names the repository for a `test.repos` pass, the reason, the resolved URL (or "none"), the head SHA (`git -C "<tested-path>" rev-parse HEAD` once the pass checked the branch out — `<tested-path>` being the worktree or the repository path step 1 used — else the PR's `headRefOid` from `gh pr view --repo "<owner/repo>" "<N>" --json headRefOid`), and what would make the pass verifiable:
   - a `test.repos` pass — declare `url` and `start` on the `test.repos.<repo>` entry;
   - a flat-block or no-entry pass — declare `test.url` and `test.start`;
   - a no-entry gap from Entry selection's row 1 — declare a `test.repos.<repo>` entry, with `url` and `start`, for each UI repository the ticket touches;
   - a no-entry gap from its row 3 (the ticket declares no `repos:`) — declare `test.url` and `test.start`, or give the ticket its `repos:`;
   - an absent branch — the ticket's `repos:` names a repository the assembled branch does not exist in;
   - a driver pass whose driver could not run — run `/verify:setup`; a headless run also needs the Bash allow rule for the driver (`docs/advanced.md`, Ship flags). Its reason names the failing `doctor` fields or the `launch` error's first line, never a log tail.

   Only a `start` booted during the pass establishes that the URL serves the PR head. The comment posts exactly as step 3 does, but with no `--attach` and no evidence marker — a nonce heredoc into a `mktemp -d` file, then `gh pr comment --repo "<owner/repo>" "<N>" --body-file "<file>"` — with `<N>` and `<owner/repo>` controlled values and the SHA a command-substitution value; neither the URL nor any agent text is interpolated into the command. The pass then records the gap in the run report and the next pass runs; the run continues to the normal end-of-run PR outcome, and a failed *not verified* post is reported, never fatal. A tester that crashed or timed out is not a setup gap: it is reported in the run report only, and a failed screenshot post still posts the verdict and findings text. A ticket whose every pass degraded — a setup gap, or a tester that crashed or timed out — is not written, so it keeps the `05-tests.md` its close stage wrote; a failed step-4 write is reported, naming the ticket and the artifact, and the run continues. Mirrors the test-checkpoint's non-blocking skip in [`test-preflight.md`](../../close-stage/references/test-preflight.md) §6 — a UI-test setup gap, a failed behavioral check or a layout finding is recorded, never fatal, and never blocks or alters the resulting-PR outcome.
