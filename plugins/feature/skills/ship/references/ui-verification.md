# Ship — end-of-run UI verification (`--ui-test` only)

Read this file only when `--ui-test` was passed (default is no browser pass). The pass runs **after** the resulting PR(s) are open (END OF RUN in ship's SKILL.md) and **before** any `--merge` — the evidence has to land on an existing PR, and on a `--merge` run it's what the human still gets. It never changes the PR outcome; a setup gap or a behavioral failure is reported and the run continues to its normal open/merge ending.

**Supported `--ui-test` contract (what "evidence on the PR" means).** The per-AC behavioral **verdict** always reaches the PR. **Screenshots** reach it *inline* only where they are hostable — i.e. where the consumer versions the ticket folder (step 3, Tracked); where the consumer gitignores `claudedocs/` (Ignored) they are referenced by their run-local path. Path-only degradation is a **documented, supported outcome, not a broken promise** — inline visual evidence deliberately requires the ticket folder to be versioned. Universal inline embedding regardless of `.gitignore` (uploading each shot as a Release/gist asset and embedding the asset URL) is **not part of this contract** — do not improvise it; every "post the screenshots" phrasing below resolves to this contract.

The assembled branch is the first point the whole UI story is testable, and the orchestrator runs in main context where browser MCP is reachable. Spawn **one** `ui-tester` subagent per run (one browser session, not per ticket) to run the acceptance criteria's behavioral checks against the assembled branch, then post its UI-test evidence (the behavioral verdict plus the screenshots — inline when the ticket folder is tracked, else a path manifest; see step 3) to the resulting PR:
- **Epic run** → assembled branch is `integration/<epic-id>`; the evidence posts to the integration PR.
- **Solo run** → assembled branch is the ticket's open PR head; the evidence posts to that PR.
- **Multi-solo run** → the one end-of-run pass walks each ticket's open PR head in turn, posting each ticket's evidence to its own PR. Each ticket is a distinct branch and app-state, so the single session re-runs the pre-flight per ticket — re-check-out that ticket's branch (`git checkout <ticket-branch> && git pull --ff-only`) and, if `test.start` booted the app, re-boot it (with its own §4 teardown) — before that ticket's behavioral checks and screenshot post.

1. **Pre-flight (reuse, do not reinvent).** Resolve the app URL + auth as [`../../build/references/test-preflight.md`](../../build/references/test-preflight.md) prescribes — §1 URL resolution from the project `test:` block (`test.url` → CLAUDE.md hint → dev-port probe, held as a data value), §2 reachability `curl`, §3 optional `test.start` boot + bounded poll with §4 teardown, §5 auth recipe (`storage_state` → `attach_tab`) composed into the spawn prompt. That reference is the single source of truth for the recipe — don't restate it here, with **one ship-specific substitution**: §3 materializes the launch script with the `Write` tool, which ship's orchestrator doesn't carry (it has Bash but no Write — see step 3). Materialize the **same fixed-path script** (`/tmp/fp-test-preflight-<id>.sh`, entire body = the `test.start` value) with a **single-quoted heredoc whose delimiter is a verified-unique nonce** — confirm the nonce line does not occur in the `test.start` value before writing — the same mechanism step 3 uses for comment bodies. A single-quoted heredoc performs no expansion, so quotes / `$()` / backticks in the declared command land as file content, preserving §3's no-shell-reparse guarantee; everything else in §3 (fixed path, PID capture, bounded poll, §4 teardown) applies unchanged. §3's PID/script files are keyed on a stable id: use `<epic-id>` for the epic pass (whose assembled branch is `integration/<epic-id>`, not one ticket) and the ticket-id for the solo/multi-solo passes. Check out the assembled branch first (`git checkout <assembled-branch> && git pull --ff-only`) so the running app reflects the code under test.
2. **Spawn.** Give the `ui-tester` subagent (subagent_type `feature:ui-tester`) a self-contained brief: the acceptance criteria to verify behaviorally — the `<AC_SOURCE_BLOCK>` resolved per ship's storage file §3 — the pre-flight-resolved reachable URL, the §5 auth recipe, and an instruction to capture a screenshot per acceptance criterion at the evidence home ship's storage file §7 names.

   It judges **behavior** (flow completes, elements respond, no console errors, right text renders); it does not judge alignment/aesthetics — that's the human's job from the images.
3. **Post the evidence to the resulting PR**, following [`../../review/references/pr-comments.md`](../../review/references/pr-comments.md) §7 injection discipline. `gh pr comment --body-file` posts **text only** — it can't reproduce the web UI's paste-to-upload (that hits GitHub's private `user-attachments` asset endpoint, which `gh`/the public API doesn't expose), so it can only reference an **already-hosted** URL. Whether the screenshots are hostable is decided per ship's storage file §7, which selects one of the two outcomes below:
   - **Tracked** (the consumer versions the ticket folder) → the screenshots are committed and pushed with the assembled branch, so they're hostable. Commit them (subject `<id>: ui-test screenshots`), push to the assembled branch, capture the pushed commit SHA, and **embed each inline** by **commit-SHA** raw URL — `https://github.com/<OWNER>/<REPO>/blob/<pushed-sha>/<path>?raw=true` (SHA, never the branch name, so the link survives the `--merge` `--delete-branch`). Real visual evidence on the PR.
   - **Ignored** (e.g. a plugin repo that gitignores `claudedocs/`) → the screenshots stay local run artifacts; there's nothing to host, so post the per-AC verdict plus a **manifest of their file paths** (never claim they're attached). This is the supported path-only outcome (above), not a gap — a consumer that wants inline screenshots on the PR versions its ticket folder, or waits for the deferred Release-asset upgrade.

   Either way the orchestrator has Bash but no Write tool, so materialize the comment body the way the reviewer hop does — a §5 quoted-heredoc into a `mktemp -d` file with a verified-unique nonce delimiter — then post with `gh pr comment "<N>" --body-file "<file>"`: `<N>` a controlled integer, `<OWNER>`/`<REPO>`/`<pushed-sha>` command-substitution values, never a `--body "…"` literal, never interpolating agent-generated text or file paths into the command, never `eval`. The verdict always reaches the PR; the images reach it inline wherever the ticket folder is versioned, and degrade to an honest path manifest where it isn't — never dropped, never overclaimed as embedded.
4. **Degrade, never block.** If the app is unreachable, there's no `test:` config or resolvable URL, or the browser MCP isn't available, **report it in the run report and continue** to the normal end-of-run PR outcome. Mirrors the test-checkpoint's non-blocking skip in [`../../build/references/test-preflight.md`](../../build/references/test-preflight.md) §6 — a UI-test setup gap or a failed behavioral check is recorded, never fatal, and never blocks or alters the resulting-PR outcome.
