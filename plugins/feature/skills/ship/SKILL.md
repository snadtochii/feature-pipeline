# Ship — autonomous build → independent review → resulting PR

`ship` is the autonomy layer **on top of** `/feature:flow`. Flow builds one ticket and (with `--pr`) opens a PR. `ship` wraps that in four things flow does not do:

1. **An independent, bias-isolated reviewer** — a separate subagent that reviews the PR against the spec + diff *only*, never the implementer's own narrative of why the code is correct, and posts findings to GitHub.
2. **Self-validation + address** — the implementer fetches the posted review, judges each finding against reality (reviewers can be wrong), and fixes the real ones. **No per-ticket human gate** — in an epic run it then squash-merges the per-ticket PR into the integration branch; the human gate is the resulting PR(s) (item 4).
3. **A sequential loop** — in an epic run, after each per-ticket merge the orchestrator pulls the integration branch (so the next child plans against merged code) and advances; load-bearing for `blocked_by` chains: child N+1 must see child N merged before it plans. In a multi-solo run the tickets are independent, so each ships off `<base>` with no between-ticket pull. Opt-in `--parallel` runs *independent* tickets concurrently — in a multi-repo workspace partitioned into per-repo lanes, with isolated worktrees only where one repo runs two or more tickets at once — while keeping merges and state writes serialized (see Arguments).
4. **Resulting PR(s) as the human gate (open by default)** — every run ends at one or more open PRs targeting the base branch (`--base`, default `main`): a **solo** run's single-ticket PR, a **multi-solo** run's N independent single-ticket PRs (one per ticket), or — for an **epic** run — one integration→`<base>` PR collecting the per-ticket PRs that merged into `integration/<epic-id>` (cut from `<base>`). `ship` leaves the resulting PR(s) open for you to review; pass `--merge` to have ship merge them (solo/multi-solo: squash each; integration: merge commit, preserving the per-ticket squashed commits). If branch protection blocks a `--merge`, ship stops and reports.

> **Autonomy with a final gate.** `ship` runs each ticket end to end without a per-ticket human gate — it decides, fixes, and (in an epic run) merges per-ticket PRs into the integration branch on its own, stopping only on a *genuine* blocker (see Guardrails). The human gate is the **resulting PR(s)**: ship opens them and leaves them open unless you passed `--merge`. If you want to gate every child's merge into the integration branch instead, use `/feature:flow --pr` directly and merge by hand. This skill is **user-initiated only** (`disable-model-invocation: true`) — Claude will not auto-run it; invoke `/feature:ship` deliberately.

## Topology

The orchestrator (this skill, in the main conversation) drives the **outer loop**: it resolves the run shape (classified in SETUP step 1; branch strategy in step 3), spawns subagents, and independently verifies each hop from evidence the implementer did not produce (Hop verification, under PER TICKET). It never edits ticket code itself.

**Environment requirement (applies to all of `ship`).** The orchestrator needs async child observation and three nested child layers: implementer → stage → reviewer/explorer/UI role. Check the selected runtime’s actual depth and concurrency limits before dispatch; the runtime’s Capacity operation reserves descendant slots and reports missing capabilities. Flow loads inline inside the implementer and adds no extra child layer.

The orchestrator spawns each role directly — implementer, then the independent reviewer as its sibling, then an implementer to address the review. The tree stays shallow and the orchestrator can observe and recover each hop. Per ticket, in `blocked_by` order (epic run) or list order (multi-solo run):

```
orchestrator (main)
  ├─ epic run (resolved ID is kind: epic): create integration/<epic-id> off <base> (base for every per-ticket PR)
  ├─ solo run (one parentless ID) / multi-solo run (2+ parentless IDs): no integration branch — each ticket's PR targets <base> and is a resulting PR
  └─ per ticket, in blocked_by order (epic) or list order (multi-solo):
       1. implementer subagent → Skill feature:flow <id> --pr --no-ui-testing [--worktree]   (plan → implement → review → close → open PR against <BASE_BRANCH>)
       2. orchestrator: Hop verification + provenance comment → reviewer subagent → spec + diff only → posts PR review
       3. implementer subagent → Skill feature:address-review <n> --auto (validate → fix → reply → push) → epic run: PR checks green → gh pr merge --squash into the integration branch; solo/multi-solo: leave the PR open
  ├─ orchestrator: verify the hop (Hop verification; epic run: merge landed; solo/multi-solo: PR open) → next ticket
  └─ end of run: the resulting PR(s) — epic run: one open integration→<base> PR; solo/multi-solo: the already-open ticket PR(s). Left open unless --merge.
```

Roles stay separated: the implementer owns build + fix authority (and per-ticket merge authority in an epic run); the reviewer is independent and adversarial. The orchestrator **independently verifies every hop** — do not trust the implementer's self-report; check the branch and PR state yourself and read evidence the implementer did not produce: the PR's checks beside the close stage's record (Hop verification, under PER TICKET). Independence is about who reads the result, not about re-executing the suite the pipeline already ran; a local run is reserved for a PR that reports no checks.

## Arguments

```
/feature:ship $ARGUMENTS
```

- `$1 …` = one or more IDs to ship, in the order given — solo ticket IDs (e.g. `PB-14 PB-15`), an epic ID, or a single epic child shipped directly. The run shape — **epic**, **solo**, or **multi-solo** — and what it means for branches and PRs are classified from the resolved tickets in SETUP step 1 (branch strategy in step 3).
- `--base <branch>` = the trunk of the run (default `main`): the branch feature/integration branches are cut from and the branch the **resulting PR(s)** target. It does not change the branch strategy (SETUP step 3).
- `--merge` = merge the **resulting PR(s)** into `<base>` at the end of the run instead of leaving them open. Solo/multi-solo single-ticket PRs: `gh pr merge --squash` (each); integration→`<base>` PR: `gh pr merge --merge` (a merge commit, so the per-ticket squashed commits survive on `<base>`). In an epic run, per-ticket merges into the integration branch happen regardless of this flag — the chain needs them to build on merged code. If branch protection (required reviews, status checks) blocks the merge, ship STOPs and reports; it never forces.
- `--parallel [N]` = opt-in concurrent walk (default off — the walk is serial). Dispatches every **ready** ticket — all `blocked_by` dependencies terminal — as a concurrent implementer subagent in its own isolated git worktree, up to N in flight (N optional, default 3), greedily dispatching newly-unblocked tickets as workers finish. Applies to epic runs and multi-solo runs (a solo run has one ticket — nothing to parallelize); a pure `blocked_by` chain yields a ready set of one at a time, so it walks like the serial path. Integration merges, ticket state transitions, and `_lessons.md` writes stay orchestrator-serialized; a failed worker doesn't abort its siblings. In a multi-repo workspace the run is partitioned into **repo lanes** from the tickets' `repos:` frontmatter: lanes run concurrently against their own repo checkouts (cross-repo parallelism needs no worktrees), and worktrees are provisioned only for a lane running ≥2 of its tickets at once; N stays one global cap across lanes. Requires the project's worktree setup contract (a `worktree:` block in `claudedocs/tickets/config.yaml` — see `docs/advanced.md` §Worktree setup) — in a multi-repo workspace only for lanes doing intra-repo concurrency; without it, or when worktree setup fails mid-run, ship logs why and degrades to the serial walk (per lane, in a lane run). Mechanics live in [`references/parallel-walk.md`](references/parallel-walk.md), read only when this flag is set.
- `--worktree` = build each ticket in a dedicated git worktree on the **serial** walk, forwarded to `flow` (which forwards it to `build`; mechanics in [`../build/references/worktree.md`](../build/references/worktree.md)). Two interactions, both resolved at SETUP step 4: with `--parallel` it is **redundant** — that walk already provisions a worktree per dispatched ticket — so it is dropped with a one-line notice. And on a run whose `<BASE_BRANCH>` is not the repository's own `origin/HEAD` default it is **dropped with a notice** too — covering both an epic run's `integration/<epic-id>` and a solo run under `--base <non-default>`: neither `flow` nor `build` takes a base argument, so build resolves `origin/HEAD` and would cut the worktree from the default trunk while the PR targets something else. `--parallel` is the isolation path for a chain; it provisions directly from the bound base.
- `--ui-test` = opt-in end-of-run browser pass (default off — no UI verification). When passed, after the assembled branch is green and the resulting PR(s) are open, ship spawns **one** `ui-tester` subagent from main context to run the acceptance criteria plus build's required UI checks against the assembled branch and posts the screenshots to the resulting PR (see END OF RUN → UI verification). It governs **only** this end-of-run pass — every per-ticket build still runs headless (`flow … --no-ui-testing`). Without `--ui-test`, browser-level acceptance-criteria verification is deferred to the human at the resulting PR (post-merge on a `--merge` run). A setup gap posts a *not verified* comment to the PR and a UI-test failure is reported; neither is fatal — the run still ends at its normal PR outcome.

### Examples
```
/feature:ship PB-13                       # solo → open single-ticket PR into main
/feature:ship PB-13 --merge               # solo → squash-merge that PR into main once green
/feature:ship PB-14 PB-15                 # multi-solo → an independent PR per ticket into main, each left open
/feature:ship PB-14 PB-15 --merge         # multi-solo → squash-merge each PR into main once green
/feature:ship PB-11                       # epic (PB-11 is kind: epic) → children in dependency order → integration/PB-11 → open integration→main PR
/feature:ship PB-11 --merge               # epic → same, then ship merges the integration→main PR (merge commit)
/feature:ship PB-11 --ui-test             # epic → end-of-run browser pass on integration/PB-11, screenshots posted to the integration PR
/feature:ship PB-11 --parallel            # epic → independent children build concurrently, ≤3 worktrees in flight
/feature:ship PB-14 PB-15 --parallel 2    # multi-solo → both tickets build concurrently (edge-free = all ready at once)
```

### Flags ship does not take
- **`--pr` is implicit.** `ship` always builds with `flow --pr` — autonomy needs a PR to review and address — so you never pass it.
- **`--no-ui-testing` is implicit *down to `flow`*.** `ship` always builds each per-ticket ticket with `flow … --no-ui-testing` — mid-chain a feature is half-assembled and the implementer subagent can't reach browser MCP anyway, so the browser/`ui-tester` checkpoint is skipped while lint + typecheck still run and still gate each build's verdict. You never pass `--no-ui-testing` yourself; it's always on for the per-ticket builds. The only browser pass ship offers is its own end-of-run `--ui-test` (above) — the one point the whole UI story is testable from main context.

## Procedure

### SETUP
**Runtime.** Bind the runtime and plugin root per [../flow/references/runtime.md](../flow/references/runtime.md). Its operations apply to every implementer, independent-reviewer, address and UI-test child, and every nested skill invocation. Prefix each child brief with its resolved runtime block; preserve it through recovery and flow’s stage spawns. Apply the runtime’s capacity reservation before dispatching workers, including on the parallel walk.

**Storage mode.** Detect it once per run per [`../flow/references/storage.md`](../flow/references/storage.md) §Mode detection, then read ship's storage file for that mode — [`storage-fs.md`](references/storage-fs.md) / [`storage-server.md`](references/storage-server.md) — **once here, in full**; every later `§N` cite in this skill refers to that already-loaded file, and ship's references cite it by name as "ship's storage file §N". Subagent briefs inline what §3 resolves; a subagent never follows a storage reference itself.

1. **Resolve the ticket list and classify the run shape** — by the resolved tickets' identity, not by how many IDs or which flags were passed. Read each resolved ID's metadata per §1 (`kind`, parent linkage, `blocked_by`, and — under `--parallel` — the lane-partition input step 4 consumes):
   - **Epic run** — exactly one resolved ID, and it is `kind: epic`. Ship its *materialized* children, in `blocked_by` topological order — the roster per §1, with any skipped IDs listed in the run report.
   - **Solo run** — exactly one resolved ID that is **not** `kind: epic`. This covers a parentless solo ticket *and* a single epic child shipped directly (`parent:` set) — a lone child is a legitimate unit of work (as it is for `flow`/`build`), so ship it alone on its own feature branch off `<base>` with a single-ticket PR to `<base>`; its `blocked_by` deps are enforced by the blocker check below.
   - **Multi-solo run** — two or more resolved IDs, all parentless solo tickets (none `kind: epic`, none with `parent:` set). Ship each independently, in the order given.
   - **Guard (multi-ID lists only; STOP before building)** — a multi-ID list must be all parentless solo tickets. STOP and report if it contains:
     - any **epic child** (`parent:` set) → tell the user to ship its epic instead: `/feature:ship <parent-epic-id>` (an epic run walks the children in dependency order on an integration branch). Name each offending ID and its `parent`. Dependency resolution belongs to the epic run — never ship epic children as an ad-hoc independent-PR list.
     - any **epic ID** (`kind: epic`) → an epic ships on its own: `/feature:ship <epic-id>` alone. Don't combine an epic with other IDs in one list.
   - Every single-ID input is classified (epic run if `kind: epic`, else solo run) and every multi-ID list is either a multi-solo run or a guard STOP — the classification is total.
   - **Blocker check (every run)** — confirm each shipped ticket's `blocked_by` deps are already `done`/merged. In an epic run, order the children so deps merge first. In a solo or multi-solo run, an unmet `blocked_by` is a STOP (the dependency isn't in place) — surface it and direct the user to ship the dependency first (or its epic). Exception, `--parallel` only: a blocker that is itself one of the run's tickets is not a STOP — defer it to the parallel walk's ready-set (`references/parallel-walk.md` §2), which holds the dependent undispatched until that blocker is terminal in-run; this is what lets a multi-solo `--parallel` list carry `blocked_by` edges (including cross-repo ones) between its own tickets. If the dependency's PR is already merged but the ticket still reads unmet, run `/feature:sync` to reconcile it to `done/`, then re-run.
2. Pre-flight: `git checkout <base> && git pull --ff-only` (default `main`), confirm a clean tree and `gh auth status` is logged in. (`--parallel` in a multi-repo workspace: the git portion runs per lane repo via the lane record — `references/parallel-walk.md` §1 — since the workspace root is not a git repo; `gh auth status` once.) Read the repo's CLAUDE.md for the project's load-bearing constraints. For carry-forward lessons, consume the project's lessons store per the shared contract in [`lessons-log-fs.md`](../flow/references/lessons-log-fs.md) / [`lessons-log-server.md`](../flow/references/lessons-log-server.md) §8 — the store per §2 — match by the subject keywords the shipped tickets touch, never full-load the store — and pull only the matching atomic entries into the per-ticket brief; no store, or no match → carry no lessons block.
3. **Resolve the branch strategy** — from the run shape classified in step 1:
   - **Solo or multi-solo run** → no integration branch. `<BASE_BRANCH>` = `<base>` for every ticket; each ships on its own feature branch (build names it from the ticket ID) and opens its own single-ticket PR against `<base>`. A solo run's one PR — and each of a multi-solo run's N PRs — is a resulting PR of the run.
   - **Epic run** → create an integration branch off `<base>` and use it as `<BASE_BRANCH>` for every per-ticket PR — even when only one child is materialized right now (later siblings join the same branch). Name it `integration/<epic-id>`. Create it once and push it: `git checkout <base> && git pull --ff-only && git checkout -b integration/<epic-id> && git push -u origin integration/<epic-id>`. If it already exists (resume), reuse it.
4. **Parallel gate (`--parallel` only), and the `--worktree` interactions.** Resolve `--worktree` first — both of its interactions are decidable here, before any dispatch. With `--parallel`, drop it: `--worktree: redundant with --parallel, which already provisions a worktree per dispatched ticket; ignoring it.` Without `--parallel`, compare `<BASE_BRANCH>` (bound at step 3) against the repository's default — `git symbolic-ref --short refs/remotes/origin/HEAD | sed 's@^origin/@@'`. Different → drop it too: `--worktree: this run's base is <BASE_BRANCH>, not the repo default, and flow cannot convey a base to build's provisioning — the worktree would fork from the default trunk. Ignoring it; use --parallel for isolation on a chain.` Testing against the repo default rather than `<base>` is what makes this fire on `--base <non-default>` as well as on an epic's integration branch — a solo run sets `<BASE_BRANCH>` = `<base>` by definition, so a `<BASE_BRANCH>` ≠ `<base>` test would miss it. Otherwise `--worktree` survives and the serial walk's Step 1 forwards it (PER TICKET below). Then, if `--parallel [N]` was passed, the **mixed-repo epic guard**: in an epic run, if the children's `repos:` frontmatter spans more than one repo, STOP and report — name the epic and the repos its children span, and direct the user to ship it per-repo instead (the integration branch cannot span repos). Otherwise read [`references/parallel-walk.md`](references/parallel-walk.md) now and follow it: it keeps every PER TICKET hop, brief, verification, and guardrail below, but replaces the one-ticket-at-a-time iteration with ready-set dispatch — in a multi-repo workspace partitioned into per-repo lanes — into isolated worktrees where a lane needs them, and names the serialization points the orchestrator owns. If the project has no `worktree:` block in `claudedocs/tickets/config.yaml`, log that `--parallel` needs the worktree setup contract and continue with the serial walk below (in a multi-lane run this degradation is per lane — see the reference's §1 repo lanes). With neither `--worktree` nor `--parallel`, skip this step — nothing below changes.
5. TodoWrite one item per ticket.

### PER TICKET (loop)
Each ticket runs three roles — **implementer → independent reviewer → implementer (address; merge in an epic run)** — and the orchestrator spawns each as its own `Task` (implementer for Step 1, reviewer for Step 2, implementer for Step 3). Spawn full-tool subagents (implementer subagent_type e.g. `claude`; reviewer `general-purpose`) with **self-contained briefs** — subagents do **not** share your context. Every brief must carry:

- **Role + full autonomy** (no per-ticket human gate; decide and record reasoning).
- **Repo path + ticket identity**, including whether it's an epic child and its spec — the `<TICKET_ARG_BLOCK>` resolved per §3.
- **Base branch** = `<BASE_BRANCH>` (the integration branch in an epic run, else `<base>`). Cut the feature branch from `<BASE_BRANCH>`, and target the PR at it.
- **Project conventions that override harness defaults** — for feature-pipeline repos: commit subject `<ID>: <imperative>`, **no `Co-Authored-By` trailer**, one concern per commit; plus any boundary rules from CLAUDE.md (e.g. this app's server/client `node:*` boundary).
- **Step 1 — Build:** invoke `Skill feature:flow` with args `<ID> --pr --no-ui-testing` — plus `--worktree` when it survived SETUP step 4. Ensure the PR's base is `<BASE_BRANCH>`: the brief names `<BASE_BRANCH>` explicitly as both the branch to fork from and the PR target, and `flow --pr` auto-detects a base on its own — so after the PR opens, check `gh pr view <n> --json baseRefName` and retarget with `gh pr edit <n> --base <BASE_BRANCH>` if it differs. Never repoint `origin/HEAD` to steer the base — `refs/remotes/origin/HEAD` is repo-level state shared by every worktree of the clone, not run state. Do not validate after the close stage returns — the pipeline's validation is on record, and the orchestrator verifies the hop (Hop verification). The PR body is the `06-summary.md` the close stage's finalizer writes, which never carries the implementer's `## Rationale` — do not edit it; the independent reviewer (Step 2) reads it (bias isolation). A close that ends at a verdict other than `pass` opens no PR: report it as a blocker, and the orchestrator spawns no reviewer for that ticket.
- **Step 2 — Independent review:** before the spawn, the orchestrator runs Hop verification on the Step 1 PR — red checks here are not a blocker: they go into Step 3's brief as named failing checks to fix alongside the review. Then it posts the inner-cycle review provenance as a **PR comment** (not in the body): one line composed from the review stage's result in `04-review.md` (read per §9), e.g. "Review stage: 4 parallel reviewers — zero findings at confidence ≥ 80", written to a temp file and posted with `gh pr comment <n> --body-file <file>` — never a pasted literal, and never finding text. A failed post (e.g. `gh` auth) is not a verification failure: record it under blockers and continue to the spawn. Then the orchestrator spawns ONE reviewer subagent (`general-purpose`) using the reviewer prompt template — read [`references/reviewer-prompt.md`](references/reviewer-prompt.md) at this spawn and inline its template verbatim into the brief, with the real PR number. The reviewer gets the spec path + PR diff + neutral instructions only — **never** the implementer's justifications; the PR body it reads is the close stage's summary, never the comments or the full inner-cycle findings — bias isolation.
- **Step 3 — Address (merge in an epic run):** invoke `Skill feature:address-review <n> --auto` — it fetches the actually-posted review, validates each finding (ACCEPT real / DISMISS wrong, one-line reason each), fixes the accepted ones, pushes, and posts signed replies. `--auto` is the unattended path (no interactive gate). When Step 2's Hop verification found red checks, the brief names each failing check to fix alongside the review. Then, **in an epic run**, the merge into the integration branch is gated on the pushed head, and the brief states the run's CI state — the orchestrator inlines its "no CI on PRs" decision, which the implementer cannot read from the orchestrator's todo. **With CI on PRs**: `gh pr merge <n> --squash --delete-branch` once Hop verification item 1's read reports green for the pushed head; red, a watch that times out while pending, or no checks registered for that SHA → blocker, no merge. **On a run recorded as having no CI on PRs**, the brief overrides this merge clause: the implementer stops after address + push, and the orchestrator runs Hop verification on the pushed head (its local fallback on the PR branch) and, when green, runs that merge itself — the parallel walk's verify-then-merge order. **In a solo or multi-solo run**: leave the PR **open** — it is a resulting PR of the run; whether it merges is decided at END OF RUN (`--merge`). The split: `address-review` does the code fix + signed replies; ship reads the evidence (Hop verification, after this hop) and merges. Red checks after this hop are a blocker. Either way, what lands is **code only** — the ticket folder stays in `review/` (status `in-review`); finalizing it to `done/` is `sync`'s job (see Ticket-state finalization under END OF RUN).
- **Step 4 — Report** the structured sections: ticket, branch, base, pr, built, checks (the Hop verification result with its source — `PR checks <state> @ <sha>` or `local fallback (no CI on PRs): <result>`), review_findings, addressed, merge SHA (epic run) or open-PR state (solo/multi-solo), **ui_verification** (state plainly that browser ACs were **not** verified in this per-ticket loop and where verification falls instead — the resulting PR, or the end-of-run pass when `--ui-test` was set; semantics under Arguments → `--ui-test`), blockers, and **finalization** (ticket left in `review/` — run `/feature:sync` to promote to `done/`).
- **Guardrails:** spawn exactly one reviewer per ticket; never weaken/skip tests to go green; never merge the resulting PR unless `--merge` was passed; on a genuine blocker (merge protection, irreconcilable finding, unfixable test) STOP and report it instead of forcing/faking.

For a **UI ticket**, browser verification is **not** run during the loop — per-ticket builds are always headless (semantics under Arguments → `--ui-test`) — so verification relies on the pipeline's lint and typecheck plus the PR's checks, or the local fallback when the PR reports none (Hop verification). The independent reviewer still reasons about user-visible behavior from the diff.

### Hop verification
The orchestrator's evidence that a hop left the ticket green, defined once here and cited by Step 2, Step 3's epic-run merge gate and AFTER EACH IMPLEMENTER RETURNS; each runs it on the PR's **current** head.

1. **PR checks.** `gh pr view <n> --json headRefOid` for the head SHA, then `gh pr checks <n>`, read only once the checks belong to that SHA — a push moments earlier can still show the previous head's checks, so a stale green is never evidence. Pending → `gh pr checks <n> --watch --fail-fast >/dev/null 2>&1; gh pr checks <n> --json name,bucket,link` with the `Bash` timeout at the runtime's cap (600000 ms) — without a terminal the watch reprints the whole table on every refresh, so its output is discarded and only the one compact read enters the window; still pending when the watch times out → blocker, never a local run in its place (it would mask CI that is still running). Any failing check → red.
2. **Close record.** Read the ticket's close record per §9: `06-summary.md`'s validation and test lines, and `04-review.md`'s `## Post-review validation`. A record that reports red, or `none documented`, is noted in the report and never counts as green evidence.
3. **No checks.** Nothing is registered for the head SHA after one grace re-read. This is decided **once per run**: the first hop that finds it records "no CI on PRs" in the run's todo, and every later hop skips item 1 and goes straight to item 4 — an epic's PRs into `integration/<epic-id>` commonly trigger no CI configured for the trunk, and the grace wait would otherwise repeat on every hop.
4. **Local fallback — only when the PR reports no checks, at most once per hop.** Resolve the commands the way `address-review` does — the project instruction files `CLAUDE.md` and `AGENTS.md`, the current runtime's primary file first — plus the spec's verification tests, and run them against the PR's code: on its branch after `gh pr checkout <n>` (build's provisioned-branch short-circuit never checks anything out in the main checkout, and on a `--worktree` run the close stage's verdict gate removed the worktree, so without the checkout the fallback would verify `<BASE_BRANCH>` and report green regardless) — in an epic run, before the merge (Step 3); on the parallel walk, in the ticket's worktree. Never weaken or skip a test to get there.

Green = the checks green at the head SHA (or the fallback green) and the close record green; Step 4's `checks` field records the source. **Merged-state revalidation stays local**: END OF RUN's integration-branch check, the multi-solo `--merge` re-check, and the parallel walk's per-merge revalidation ([`references/parallel-walk.md`](references/parallel-walk.md) §5) each validate a tree no PR's checks ran against, so they run the suite as written there — this section does not govern them.

### AFTER EACH IMPLEMENTER RETURNS (orchestrator verifies)
**In an epic run:** `git checkout <integration branch> && git pull --ff-only`, then **independently**: confirm the merge commit is on the integration branch, `gh pr view <n>` shows `MERGED`, no stray open PR remains, and Hop verification on the merged PR's head is green — the serial walk forks each ticket from the current integration head and nothing else merges in between, so the squash result is the tree its checks ran on. On a run with no CI on PRs, the pre-merge Hop verification Step 3 ran is this hop's evidence and is not repeated. **In a solo or multi-solo run** nothing merges by design: confirm the ticket's PR is **open** and targets `<base>` (`gh pr view <n> --json state,baseRefName`), no stray extra PR exists, and Hop verification on the PR's head is green. **Every run shape**: apply §4's post-PR linkage step. In a multi-solo run the next ticket's implementer forks fresh from `<base>` (there is no integration branch to pull between tickets). Only then mark the todo done and advance. If verification fails, treat it as a blocker — do not start the next ticket on a broken base.

### END OF RUN (the resulting PR(s))
**Epic run** — after every child has merged into the integration branch and verified green:
1. Confirm the integration branch is green as a whole: `git checkout integration/<epic-id> && git pull --ff-only`, then `npm run typecheck`, the test suite, and `npm run build`.
2. Open the integration PR. Never paste ticket text into a quoted command literal (see `skills/build/references/pr-creation.md` for the same hardening). Resolve the epic title into `EPIC_TITLE` per §4 (a command-substitution read, never a pasted literal), then set `TITLE="<EPIC-ID>: $EPIC_TITLE"`. Write the summary (the N children shipped, each per-ticket PR #, the per-ticket review outcomes) to a temp file, then `gh pr create --base <base> --head integration/<epic-id> --title "$TITLE" --body-file <summary-file>`. Record the integration PR's linkage per §4 — ship owns this PR, so ship owns its linkage.
3. **Default**: leave it open — report the PR URL and stop; this is the human gate. **With `--merge`**: on a `--ui-test` run, run UI verification (below) and post its UI-test evidence to this PR **first** — `--delete-branch` destroys the branch the pass needs. Then merge it with a merge commit (`gh pr merge <n> --merge --delete-branch`) so the per-ticket squashed commits survive on `<base>`; if branch protection blocks the merge, STOP and report instead of forcing.

**Solo run** — the resulting PR is the single-ticket PR already open from the loop. **Default**: report its URL and stop. **With `--merge`**: on a `--ui-test` run, run UI verification (below) and post its UI-test evidence to this PR **first** — `--delete-branch` destroys the branch the pass needs. Then `gh pr merge <n> --squash --delete-branch` into `<base>`; if branch protection blocks it, STOP and report.

**Multi-solo run** — the resulting PRs are the N independent single-ticket PRs already open from the loop (no integration branch, no aggregate PR). **Default**: report all N PR URLs and stop. **With `--merge`**: on a `--ui-test` run, run UI verification (below) for every ticket and post each ticket's UI-test evidence to its own PR **first** — `--delete-branch` destroys the branches the pass needs. Then squash-merge them into `<base>` one at a time (`gh pr merge <n> --squash --delete-branch`). Each PR's checks were run against the *initial* `<base>`, so every merge moves the base out from under the remaining PRs and their green checks go stale — two independent PRs can interact through shared behavior with no textual merge conflict, so a later merge can leave `<base>` red though its own checks were green. Before merging each subsequent PR, update its branch from the now-current `<base>` and require its checks/tests to pass again against the merged base; merge only when green. If a revalidation fails, or branch protection blocks any merge, STOP and report which PRs merged and which remain open — do not force, and do not leave the run state ambiguous.

### UI verification (`--ui-test` only)
Skip this section entirely unless `--ui-test` was passed (default is no browser pass). When it was, read [`references/ui-verification.md`](references/ui-verification.md) at this point — after the resulting PR(s) are open (above) and before any `--merge` — and run the pass it prescribes: pre-flight reuse from `test-preflight.md`, one `ui-tester` spawn per run carrying build's required UI checks, evidence posted to the resulting PR(s) under the supported evidence-hosting contract (inline screenshots where the ticket folder is tracked, an honest path manifest where it's gitignored), each covered ticket's `05-tests.md` rewritten with the result and its `06-summary.md` given a `## UI verification` section, posting a *not verified* PR comment on any setup gap — it provisions no environment beyond a declared `test.start` — without ever blocking or altering the PR outcome.

### Ticket-state finalization (all paths)
A merge — per-ticket into the integration branch, or a resulting PR via `--merge` — lands **code, not ticket state**: every ticket `flow --pr` built is sitting at status `in-review` (Transition 5 — location per §5), and `ship` does **not** perform the finalize-to-`done` move (Transition 6) — `sync` owns that single transition, so `ship` does not reimplement it. Close the loop by running **`/feature:sync`**, which scans every non-done ticket, detects each merged PR, finalizes the ticket to `done`, and fires the Epic-completion predicate for epic children — Transition 6 promotes a child only once its merge commit is reachable from `<base>`, so `sync` is safe to run at any point in the run. Surface "tickets remain in review — merge the resulting PR(s), then run `/feature:sync` to finalize" as the final line of the run report so the next step is explicit.

### REVIEWER PROMPT TEMPLATE (bias isolation is the crux)
The template lives in [`references/reviewer-prompt.md`](references/reviewer-prompt.md). Read it at the PER TICKET Step 2 reviewer spawn — the one point it's consulted — and inline its template **verbatim** into the reviewer subagent's brief with `<N>` and `<REPO_PATH>` resolved, `<GROUND_TRUTH_BLOCK>` filled from §3, and `<PR_COMMENTS_PATH>` resolved under the verified plugin root (the reviewer has no ticket-store access): the subagent cannot follow relative links, so the template text itself must land in the spawn prompt (the same spawn-time injection pattern as `review-stage`'s `references/confidence-scale.md`).

## Recovery & GitHub identity

If a run stalls or dies, re-run `ship` — resumption state lives in the ticket store plus git/GitHub (feature branches, open PRs, posted reviews; in an epic run SETUP reuses an existing integration branch, while a multi-solo run has no integration branch, so its resume state is purely per-ticket). The ticket-store evidence is read per §5 (what marks a ticket as in-review, and how its existing PR is located). On re-run, inspect each ticket's actual state and resume at the **first incomplete stage** instead of restarting its sequence: a ticket at in-review (per §5) with an open PR skips Step 1 (`flow` on an in-review ticket only re-checks merge state — it does not rebuild); a PR already carrying an `fp-review` marker for its **current** head SHA skips Step 2 — run the `pr-comments.md` §3 idempotency scan (`gh pr view <n> --json headRefOid,comments,reviews`, match `head=<current-SHA>`) rather than treating any prior review comment as sufficient (the head may have moved), and never post a second review at the same head (one reviewer per ticket); a PR already `MERGED` skips to the orchestrator's verification. Only stages with no evidence in the ticket store, on GitHub, or in git re-run.

A `--parallel` run adds worktrees to that on-disk state: `git worktree list` — run in every repo whose tickets were in the run, one per lane in a multi-repo lane run — (in-flight or stale worker checkouts) plus the open PRs plus the ticket folders/statuses reconstruct where each ticket stopped. Once each worktree's branch is pushed (or deliberately discarded), remove it — `git worktree remove <path>`, then `git worktree prune` — a pushed branch carries all resumable state; the worktree carries none. Resume by re-running ship, with or without `--parallel`; the per-ticket triage lives in [`references/parallel-walk.md`](references/parallel-walk.md) §7.

Two GitHub identity facts the loop depends on:

- **Self-review is blocked** when the PR author and the reviewer's `gh` identity are the same user — the reviewer falls back from the Reviews API to `gh pr comment` (`pr-comments.md` §5, handled in the reviewer prompt template — `references/reviewer-prompt.md`). A single-identity setup means findings are *comments*, not a formal approve/request-changes review.
- **Posting and merging under the user's identity needs the user's authorization** — the harness blocks autonomous self-merge without it, and posting can trip a security-heuristic flag. Both are expected here (invoking `ship` authorizes the per-ticket integration merges; `--merge` authorizes the resulting-PR merge), but the orchestrator should still glance at what was published (`gh api repos/{o}/{r}/issues/<N>/comments`) to confirm it's appropriate review content before relying on the merge.

## When NOT to run
- You want to gate **every ticket** — approve each per-ticket merge into the integration branch, not just the resulting PR → use `/feature:flow --pr` per ticket and merge manually.
- A single stage only → `/feature:plan` or `/feature:build`.
- Reconciling already-open PRs with merged state → `/feature:sync`.
