# Multi-Repo Workspaces — the `repos` Frontmatter Convention

Canonical logic for discover's multi-repo handling. Read when Phase 1's workspace-shape detection lands on multi-repo — a single-repo workspace never needs this file. Referenced by `discover`, which writes the field. These consumers parse it: `ship`'s SETUP (`skills/ship/SKILL.md` step 1, which binds each ticket's lane on every run and stops on an epic whose children span repos), `ship`'s parallel walk (`skills/ship/references/parallel-walk.md` §1, which partitions the run into concurrent repo lanes), each stage's in-place repository ([`ticket-resolution-fs.md`](../../flow/references/ticket-resolution-fs.md) Step 3, which aims a run with no worktree at the ticket's repository), build's `--worktree` eligibility ([`worktree.md`](../../build/references/worktree.md) §1, which binds the worktree's repository from a single entry, builds in place for 2+ and skips the code check for a blocker in another repo), test entry selection ([`test-preflight.md`](../../close-stage/references/test-preflight.md) Entry selection, which selects the `test.repos` entries to browser-test for the close stage's test checkpoint and for ship's end-of-run browser pass, [`ui-verification.md`](../../ship/references/ui-verification.md)), blocker validation ([`ticket-resolution-fs.md`](../../flow/references/ticket-resolution-fs.md) Step 6, whose merged-sibling clause binds the checkout it tests from the field and whose cross-repo clause compares a named blocker's `repos:` with the ticket's), and the PR-entry refusal (`ship`, `flow --pr` and `build --pr` stop on a non-epic ticket naming 2+ repos before any code is written).

- **Record the child-repo directory names verbatim** — exact on-disk names (e.g. `big-leaves-api`, never shortened). They are the vocabulary for the `repos` frontmatter field.
- **The repos-append convention** (every `repos` mention in discover defers here): each artifact discovery writes (solo spec, epic PRD, child spec) gets `repos: [<exact-dir-names>]` **appended** as real frontmatter — never a commented placeholder; the templates carry only the fields every ticket has. A solo or child ticket names one repo, and the field is written for it anyway (explicitness beats omission once the workspace is multi-repo).
- **Which repos go in each list**, decided per artifact at its write step:
  - Solo spec — exactly one repo, from Phase 2 exploration reconciled with the Phase 3 confirmation below
  - Epic PRD — the union of the children's repos
  - Child spec — exactly one repo, from the Phase 3.5 decomposition table. A child whose scope touches two repos splits further.
- **Phase 3 confirmation** (one line of the Technical Considerations theme): "This looks like it touches `<repo-a>` + `<repo-b>` — correct?" — inferred by matching the explorer output's file paths against the detected child-repo directory names. The user's answer wins over the inference.
- **Repo gate** (Phase 3.5): the gate reads the reconciled list — the user's answer at the confirmation, or the explorer's inference when the user moved on before it. Two or more repos means Phase 3.5 lands on N>1 with per-repo children and its checkpoint runs, whatever the scope signals say. Correcting the list to one repo at the confirmation keeps N=1. Discover offers no way to keep one ticket across repos.
- **No repo matched**: ask which repo, and keep asking until the user names one. Never write `repos: []` or omit the field.
