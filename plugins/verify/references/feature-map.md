# The feature-map contract

Authoritative format for a project's feature map: the committed Markdown file that tells an
agent which features an app has, where each one is reached, and which test ids it renders.
This file fixes the map's grammar (§2), how a map is generated from a repository (§3–§7),
and how an existing map is merged when it is generated again (§8). Every writer follows
§3–§8 and every reader parses §2, so two runs over the same tree produce the same mechanical
lines, and a drift check that regenerates them agrees with the writer.

---

## §1 Purpose and readers

| Part | Meaning |
|---|---|
| Location | Committed in the project, at the path the `test:` entry's `feature_map` key names, relative to that entry's repo root: the project root for the flat `test:` block, `<project-root>/<dir>` for a `test.repos.<dir>` entry. Default `docs/verification/feature-map.md`. |
| Writer | `verify:setup` — its first run and `--refresh`. A person edits headings and manual blocks (§7); a generator never edits a manual block. |
| Readers | The pipeline's browser tester and `verify`'s own skills. A reader takes `route:` for where to navigate, `testids:` for targets, and the manual block for how a person reaches the screen and what it needs. |
| Content | Repo-derived facts — directories, route paths, test ids — and prose. The map names no external tool and is keyed by nothing but a feature's name and its `source:`. It never holds a credential, a token, an environment value or the content of any file. |

## §2 File grammar

```markdown
# Feature map

Generated by `/verify:setup`; `source`, `route` and `testids` are regenerated by `/verify:setup --refresh`. Everything between `<!-- manual -->` and `<!-- /manual -->` is yours and is never rewritten.

## inbox
source: apps/web/src/features/inbox
route: /inbox
testids: inbox-item, inbox-list, triage-badge, triage-panel
<!-- manual -->
reach: sidebar → Inbox
needs: ≥1 unreviewed item; triage panel needs a credential with `triage`
states: empty, loading, error (server unreachable)
shortcuts: j/k move, p promote
<!-- /manual -->

## settings
source: apps/web/src/features/settings
route: /settings, /settings/:tab
testids:
<!-- manual -->
reach:
needs: a signed-in session
states:
shortcuts:
<!-- /manual -->

## Removed

### billing
source: apps/web/src/features/billing
route: /billing
testids: invoice-row
<!-- manual -->
reach: account menu → Billing
needs:
states: empty
shortcuts:
<!-- /manual -->
```

| Part | Rule |
|---|---|
| Frontmatter | None. |
| Preamble | Every line before the first line beginning `## `. A first write produces the `# Feature map` title and the one prose line above; every later merge copies the preamble verbatim. |
| Feature section | A `## <name>` heading, then exactly these lines in this order: `source:`, `route:`, `testids:`, `<!-- manual -->`, `reach:`, `needs:`, `states:`, `shortcuts:`, `<!-- /manual -->`. One blank line separates sections. |
| `## Removed` | Reserved heading, always the last section when present. Its features are `### <name>` sections with the same body. **Not live**: a reader skips `## Removed` and every section under it. |

**Values.**

- `<name>` — written as the feature directory's basename, or a fallback feature's segment
  name (§4). A person may rename it; the
  merge keeps an edited heading, because a section is identified by its `source:` (§8).
- `source:` — a directory, or for a fallback feature declared in a single file that file
  (§4), relative to the entry's repo root, `/`-separated, with no leading `./` or `/` and no
  trailing `/`. Unique across live sections.
- `route:` — route paths, each beginning `/`, normalised per §5.
- `testids:` — literal `data-testid` values (§6).
- Lists (`route:`, `testids:`) are `, `-separated, sorted in byte order, and de-duplicated.
- Every line is `<key>: <value>` with one space after the colon. An empty value is the key
  with nothing after the colon — `testids:`, no trailing space.
- Lines between `<!-- manual -->` and `<!-- /manual -->` are prose owned by people (§7). The
  four keys are what a first write drafts; a person may add lines between the markers.

**Reading.** A reader splits the file on lines beginning `## `, stops at `## Removed`, takes
the three mechanical lines by their key prefix, and treats the manual block as prose. A
section with no `source:` line is not a feature to a reader.

## §3 Read rules

Generation reads the repository and writes nothing but the map file.

- **Root.** Every `Glob`, `Grep` and `Read` resolves inside the entry's repo root. Never an
  absolute path, and never a `..`, taken from an argument, the configuration or a file read.
- **Secrets.** Never read a secret or credential file: `.env*`, `*.pem`, `*.key`, `id_*`,
  `secrets*`, `*credentials*`, `.netrc`, `.npmrc`, `.pypirc`, or anything under `.git/`,
  `.ssh/`, `.aws/`, `.docker/`, `.kube/` or `.config/gh/` — the same list as the repo-read
  rules of `plugins/feature/skills/triage/SKILL.md`. An `auth.storage_state` file is never
  read either.
- **Skipped trees.** `node_modules/`, `.git/`, `dist/`, `build/`, `out/`, `coverage/`,
  `.next/`, `.svelte-kit/`, `.astro/`, `.nuxt/`, and generated route trees (`*.gen.*`, such
  as `routeTree.gen.ts`). A route that exists only in a generated file is found from the
  source files that generated it.
- **Instruction files.** `CLAUDE.md` and `AGENTS.md` at the entry's repo root, and at the
  project root when that differs, are read for auth hints only (§7).
- **Search first.** Each signal is one search across the entry's repo root, its results
  grouped by `source:` afterwards: one `Glob` for the `package.json` files that mark §5's
  app roots, one `Grep` for the §6 test-id forms, one for import
  specifiers in route files (§4's link), one per §7 signal (navigation targets, guards,
  state branches, key bindings), each with the skipped trees, the secret patterns above and
  the declared `auth.storage_state` path — relative to the entry's repo root, supplied by
  the writer, and needed only when it lies under that root — passed to the search itself as
  exclusion globs, so a search never prints a line of a file this section never reads. A file is `Read` only when a search matched it and the match
  needs its context.

## §4 Feature discovery

1. **Feature roots.** Every directory named `features` or `modules` under the entry's repo
   root, outside the skipped trees. A `features` or `modules` directory inside a candidate
   below is not a further root.
2. **Candidates.** Each immediate child directory of a feature root. Its name is the
   directory's basename; its `source:` is its path.
3. **Written features.** A candidate is written only when it carries at least one route (§5)
   or one literal test id (§6). The rest are counted in the report as candidates with
   neither.
4. **Fallback.** When no feature root yields a written feature, each top-level route segment
   is a feature: its name is the first static segment (`home` for `/`, which holds the root
   route alone), and its routes are every route under that segment — taken from the segment,
   not from the route-to-feature link below. Its `source:` is the segment's own route
   directory (`src/routes/inbox`, `app/inbox`) when it has one; otherwise a file — the
   segment's single route file (`src/routes/inbox.tsx`, `app/page.tsx` for `/`), or, for a
   route configuration, the component module its index route renders. A routes or pages
   root is never a `source:`, so segments declared as files at that root stay apart.
5. **One feature per `source:`.** Candidates are processed in byte order of their name. When
   two resolve to the same `source:`, the first is kept, the other's routes and test ids are
   folded into it, and the report names the folded one.

**Route-to-feature link.** A route belongs to a feature when its route file is, or sits
under, the feature's `source:`, or when the route file — or, for a route configuration, the module its
component, element or lazy loader names — imports from it: a relative import that resolves
under `source:`, or a non-relative specifier containing the segment pair `features/<name>` or
`modules/<name>`. A route linked to two features is listed under both, and the report names
it.

## §5 Route extraction

Only literal paths are recorded. A path computed at runtime is skipped and counted in the
report. Several families in one repo root are unioned. No family found → every `route:` is
empty and the report names the gap ("no router found").

**App roots.** The entry's repo root, and every directory under it outside the skipped trees
that holds a `package.json`, is an app root (`apps/web` in a monorepo). Each `package.json` is
`Read`; it is not a secret file.

**File-based families** are anchored and gated, so a directory convention alone never makes
a router:

- **Anchored.** A family's directories are searched only at the roots its row names, each
  relative to an app root — `apps/web/src/app/`, never an `app/` at any other depth, such as
  `src/features/x/app/`. A route's path is taken from below that root.
- **Gated.** A family is searched at an app root only when that app root's `package.json`
  lists one of the family's packages under `dependencies` or `devDependencies`. A family
  root present without its package is not a router: its files are not routes, and the
  report names it as a gap (`apps/web/src/pages without next — not routed`).

| Family | Packages | Roots, under an app root | Path derived from |
|---|---|---|---|
| TanStack Router, file-based | `@tanstack/react-router`, `@tanstack/solid-router` | `src/routes/` — its files that call `createFileRoute(` | The string literal passed to `createFileRoute(` when present; otherwise the file path under the root, `.` and `/` both separating segments. `__root` is not a route. |
| Next.js, App Router | `next` | `app/`, `src/app/` — `**/page.{js,jsx,ts,tsx,mdx}` | The directories between the root and `page.*`. `@slot` and `_private` directories are skipped. |
| Next.js, Pages Router | `next` | `pages/`, `src/pages/` — `**/*.{js,jsx,ts,tsx,mdx}` | The file path under the root. `api/**`, `_app`, `_document` and `_error` are not routes. |
| SvelteKit | `@sveltejs/kit` | `src/routes/` — `**/+page.svelte` | The directories between the root and `+page.svelte`. |
| Astro | `astro` | `src/pages/` — `**/*.{astro,md,mdx,html}` | The file path under the root. `_`-prefixed files and directories are not routes. |
| File routes under `app/routes/` (Remix, React Router framework mode) | any `@remix-run/` package, `@react-router/dev` | `app/routes/` — its files, or its folders holding `route.{js,jsx,ts,tsx}` | The file or folder name, `.` separating segments. `_index` is the parent path, a trailing `_` is stripped, and a segment in `[ ]` is an escaped literal. |
| Nuxt | `nuxt` | `pages/`, `app/pages/` — `**/*.vue` | The file path under the root. |

**Configuration families** are recognised by their call, wherever it appears outside the
skipped trees:

| Family | Signal | Path derived from |
|---|---|---|
| React Router, configuration | `createBrowserRouter(`, `createHashRouter(`, `createMemoryRouter(`, `createRoutesFromElements(`, `<Route path=` | Literal `path` values, joined with their parents' when nested in the same file. An `index` route is its parent's path. |
| Angular | `Routes` arrays: `: Routes =`, `RouterModule.forRoot(`, `RouterModule.forChild(`, `provideRouter(` | Literal `path:` values joined with their parents'. `''` is the parent's path; `'**'` is skipped. |
| Vue Router | `createRouter(` with `routes:` | Literal `path:` values joined through `children`. A catch-all (`/:pathMatch(.*)*`) is skipped. |

**Normalisation, every family.**

- Route groups — `(group)` directories and segments — and pathless layout segments
  (`_`-prefixed segments in TanStack Router and `app/routes/`) are dropped.
- `index` and `_index` resolve to the parent path.
- Dynamic segments become `:<name>`, using the parameter's own name: `$id`, `[id]`, `:id` →
  `:id`; `[...slug]`, `[[...slug]]` → `:slug`; `[[lang]]`, `($lang)` → `:lang`; a bare `$`
  splat → `:splat`.
- The path begins `/`, joins segments with a single `/`, and ends without `/` except for the
  root `/`.

## §6 Test-id extraction

`Grep` under the feature's `source:` for literal `data-testid` attributes, in these forms:

```text
data-testid="<value>"      data-testid='<value>'
data-testid={"<value>"}    data-testid={'<value>'}    data-testid={`<value>`}
"data-testid": "<value>"   'data-testid': '<value>'
```

- A match whose attribute name is directly preceded by `:`, `v-bind:`, `[` or `[attr.` is
  a binding — its value is an expression, not a test id (`:data-testid="item.id"`) — and is
  skipped and counted as templated.
- A value containing `{` or `}` is templated in every quoting form — `${id}`, Svelte and
  Astro's `{id}`, Angular's `{{ id }}` — and is skipped and counted.
- A variable or computed value is skipped and counted in the report.
- A value containing `,` or a line break is skipped and counted: it cannot be listed (§2).
- Test and story files — `*.test.*`, `*.spec.*`, `*.stories.*` and anything under
  `__tests__/` — are not searched: the map records what the feature renders.

## §7 Manual blocks

**Ownership.** The bytes from a section's `<!-- manual -->` line through its
`<!-- /manual -->` line belong to people. No generator edits, reorders, re-wraps or removes
them, line endings included.

**First draft.** A block is drafted once, by the write that creates its section. All four
keys are written, in grammar order. A value is drafted only when the repository shows it,
and is otherwise left empty:

| Key | Drafted from |
|---|---|
| `reach:` | A navigation link in a layout, sidebar or menu component whose target (`href`, `to`, `routerLink`) equals one of the feature's routes, written `<container> → <label>`, such as `sidebar → Inbox`. |
| `needs:` | An auth guard on the feature's routes (a redirect to a sign-in route in a loader or `beforeLoad`, a `canActivate` guard, a middleware matcher), or an auth hint in `CLAUDE.md` or `AGENTS.md` covering them → `a signed-in session`. |
| `states:` | Empty, loading and error branches the feature's components render — an empty-state element, a pending component, an error boundary — as a `, `-separated list of state names. |
| `shortcuts:` | Key bindings the feature registers (a hotkey hook, a `keydown` handler comparing `key`), as `<key> <action>` pairs. |

A drafted value is a short description. It never quotes a credential, a token, an
environment value, a user name, or the content of any file.

## §8 Merge

A map that already exists at the path is merged, never overwritten. The same procedure runs
for a first `verify:setup` over an existing map and for `--refresh`.

1. **Parse.** Split the file into the preamble (§2), the live sections (each line beginning
   `## ` through the line before the next one, `## Removed` excluded) and the removed sections
   (each line beginning `### ` under `## Removed`). Line endings are kept as found.
   - A section whose `<!-- manual -->` has no `<!-- /manual -->` before the next heading, or
     whose close marker has no opener, stops the merge **for this map**: the file is left
     untouched and the report names the section.
   - A section's key is the value of its first line beginning `source:`. A live section with
     no `source:` line is kept verbatim, immediately after the section that preceded it in the
     file (first in the live list when nothing did), and the report names it. A second
     section with an already-seen key is kept verbatim the same way and reported as a
     duplicate.
   - A keyed section with no `<!-- manual -->` line is merged like any other (steps 3–4) and
     gains no manual block: a block is drafted only by the write that creates its section
     (§7).
2. **Regenerate** the feature set from the tree per §3–§6.
3. **Match each generated feature** by `source:`:
   - **A live section** → replace only its `source:`, `route:` and `testids:` lines, in
     place. A missing `route:` is inserted directly after `source:`; a missing `testids:`
     directly after `route:`. The heading, the manual block and any other line are
     untouched.
   - **A removed section** → it returns to the live list: its `### ` heading becomes `## `,
     and its mechanical lines are replaced as above.
   - **No section** → a new section: `## <name>`, the three lines, and a drafted manual block
     (§7).
4. **Unmatched live sections.**
   - Its `source:` path still exists (a section a person added, or a directory that no
     longer carries a route or a test id) → kept, with its `route:` and `testids:` lines
     recomputed for that `source:` by §4's route-to-feature link and §6, empty when nothing
     matches, and replaced as in step 3. The heading, the manual block and any other line
     are untouched.
   - Its `source:` path is gone → moved under `## Removed` as `### <heading text>`, its
     body unchanged.
5. **Unmatched removed sections** stay under `## Removed` unchanged until a person deletes
   them. A generator never deletes a section.
6. **Write.** The preamble verbatim; the live sections in byte order of `source:`, with the
   unkeyed and duplicate sections placed per step 1; then `## Removed` when it holds at least
   one section — its existing sections in their existing order, newly removed ones appended
   in byte order of `source:`. Each section's own lines are written as read except the
   three mechanical lines; sections are separated by exactly one blank line; new lines end
   in `\n`.

**Empty result.** A generation that finds no feature still writes a map with the preamble
alone (a first write), or merges as above (an existing map, whose live sections then move to
`## Removed` as their directories disappear), and the report says no feature was found.

**Report counts.** Every generation reports: features written, new, returned from
`## Removed`, moved to `## Removed`; candidates with neither a route nor a test id; computed
routes and templated test ids skipped; folded, duplicate and unkeyed sections; links to two
features; router gaps, family roots skipped for a missing package (§5) among them.
