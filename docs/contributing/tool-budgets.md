# Tool budgets

Per-skill `allowed-tools` and per-agent `tools` budgets for the `feature` plugin, and the skill budgets for the `verify` plugin, with the rationale for each entry. Read before touching either frontmatter field. Unqualified `skills/` and `agents/` paths follow the root guidance file's path convention (`plugins/feature/…`); the `verify` section names its paths in full.

## Skills

Typical budget per role, expressed as unordered tool sets. The `review-stage` *skill* may write to `claudedocs/` to save its merged review artifact, the build *skill* its handoff, and the `close-stage` *skill* its test and summary artifacts, but the *reviewer agents* are read-only — they must not mutate the tree they review.

Rows listing **pipeline MCP tools** — in this table and in the Agents table below — use them only in server-native storage mode, except `setup`'s `ping`, the connector check it runs before a mode is chosen and once as `--check`'s doctor round-trip. `triage` is the one skill whose server tools are mode-independent: the inbox exists only on the server, so it calls its `inbox_*` tools and its `pipeline_*` reads whatever the project's storage mode. Every server-tool entry is dual-listed in `allowed-tools` (skills) or `tools` (agents) under both bindings — the Claude-scoped `mcp__plugin_server-native_ps__*` and the bare name (`pipeline_*`, `inbox_*` or `ping`), which stands in for Codex's `mcp__<server>__*` from the user's MCP config. The scoped prefix is derived, not authored — `skills/flow/references/storage-server.md` owns that derivation.

| `discover` (intake) | Read, Write, Edit, Glob, Grep, Bash, Task, TodoWrite + pipeline MCP tools for ticket creation (`pipeline_create_ticket`, `pipeline_update_ticket`, `pipeline_write_artifact`, `pipeline_get_ticket`, `pipeline_list_tickets`, `pipeline_list_artifacts` for partial-failure reconciliation of artifact rows) |
| `plan` (pre-plan synthesis + plan design) | Read, Write, Edit, Glob, Grep, Bash, Agent, Task, TodoWrite, AskUserQuestion (Agent / Task for Phase 1 subagents; AskUserQuestion for auto mode's batched no-default open-questions pause) + pipeline MCP tools (`pipeline_get_ticket`, `pipeline_get_artifact`, `pipeline_list_artifacts`, `pipeline_write_artifact`, `pipeline_transition_ticket`, `pipeline_list_lessons`) |

| `review-stage` (fresh-context review round + validate-then-fix) | Read, Write, Edit, Glob, Grep, Bash, Agent, Task, TodoWrite — `Bash` for the merge-base diff, the untracked-file listing and validation commands; `Write`/`Edit` for `04-review.md`, the `## Post-review` append to `03-implementation.md`, and applying accepted fixes; `Agent` / `Task` for the 4 reviewer subagents + pipeline MCP tools (`pipeline_get_ticket`, `pipeline_list_tickets` for ticket resolution and the epic refusal, `pipeline_get_artifact`/`pipeline_list_artifacts` for the working copy and the blocker context, `pipeline_write_artifact` for `04-review.md` and the handoff upsert); no transition, update or lesson tools — the stage fires no transition and captures no lessons |
| `close-stage` (test checkpoint, verdict, gate, finalizer handoff) | Read, Write, Edit, Glob, Grep, Bash, Agent, Task, TodoWrite — `Bash` for the pre-flight `curl`, the `test.start` boot and teardown, fix validation, the `review/` row's `gh`/`git` merge predicate, base resolution for the finalizer prompt, the evidence-home `wc -c` listing every browser pass issues for `05-tests.md`'s `## Screenshots` section, a driver pass's `printenv HOME`, pass-directory `mkdir`/`rm -rf` and the installed browser driver's `doctor`, `launch` and `cleanup` verbs, and — server-native only — the `command -v personal-server` probe and the `personal-server asset upload` call that hosts those captures; `Write`/`Edit` for `05-tests.md`, `06-summary.md`, the `## Post-test` append, inline test fixes and lessons; `Agent` / `Task` for the `ui-tester` and the finalizer. The post-gate mechanics — commit, push, PR creation, PR linkage, the transition(s), worktree teardown — run in the finalizer child on its own budget + pipeline MCP tools (`pipeline_get_ticket`, `pipeline_list_tickets` for resolution and the epic roster, `pipeline_get_artifact`/`pipeline_list_artifacts` for the working copy, `pipeline_write_artifact` for `05-tests.md`, `06-summary.md` and the handoff upsert, `pipeline_transition_ticket` for `continue-with-hint`'s Transition 4 and the merge-check row's Transition 6, and the lesson tools `pipeline_add_lesson`/`pipeline_list_lessons`/`pipeline_update_lesson`/`pipeline_delete_lesson`); no `pipeline_update_ticket` — the finalizer records `pr_url` |
| `debug` (standalone runtime debugger) | Read, Write, Edit, Glob, Grep, Bash, TodoWrite + additive-optional browser-capture MCP subset (Playwright/Chrome read/observe) + pipeline MCP tools for ticket resolution, the ticket-scoped debug report, and lesson capture (`pipeline_get_ticket`, `pipeline_write_artifact`, `pipeline_add_lesson`); no `Task` |
| `sync` (standalone PR reconciler) | Read, Glob, Grep, Bash, Edit, TodoWrite — `Bash` for `gh` PR-state reads plus, fs-native, the Transition 6 folder `mv`; `Edit` for the fs-native `status` frontmatter flip + pipeline MCP tools (`pipeline_list_tickets` for the status-derived scan set, `pipeline_get_ticket` for single-ticket resolution and CAS re-reads, `pipeline_transition_ticket` for Transition 6, `pipeline_update_ticket` for the `pr_url` back-fill); no `Task` |

| `address-review` (standalone PR feedback addresser) | Read, Write, Edit, Glob, Grep, Bash, TodoWrite — the mutating sibling of `review`: `Bash` for `gh` review-comment reads + signed reply posts, `Write`/`Edit` to apply accepted fixes, `TodoWrite` to track threads; no `Task` (inline for cross-platform/headless parity), no MCP |
| `ship` (standalone autonomous build→review→merge loop) | Read, Glob, Grep, Bash, TodoWrite, Agent, Task — `Agent` / `Task` to spawn the per-ticket implementer subagent (one per ready ticket, each in an isolated git worktree, under `--parallel`), `Bash` for `git`/`gh`/test verification of each merge plus worktree provisioning/removal, and — on an end-of-run UI pass — the evidence-home `wc -c` listing for each covered ticket's `## Screenshots` section, a driver pass's `printenv HOME`, pass-directory `mkdir`/`rm -rf` and the installed browser driver's `doctor`, `launch` and `cleanup` verbs, plus, server-native, the `command -v personal-server` probe and the `personal-server asset upload` call; orchestrates `feature:flow` + an independent reviewer and never edits ticket code itself + pipeline MCP tools (`pipeline_get_ticket`/`pipeline_list_tickets` for run-shape classification + the derived epic roster, `pipeline_update_ticket` for `pr_url` linkage — the integration PR on the epic row, plus per-ticket backfill, `pipeline_get_artifact`/`pipeline_list_artifacts` for reviewer ground truth (spec body inlined into the independent reviewer's brief) and recovery's artifact-trail inspection, `pipeline_list_lessons` for the pre-run gotcha scan + reviewer lesson injection; `pipeline_transition_ticket`/`pipeline_add_lesson`/`pipeline_update_lesson` only at `--parallel`'s orchestrator serialization points, where the orchestrator owns the transitions and lessons writes workers skip; `pipeline_write_artifact` only for the end-of-run UI pass's write-back of each covered ticket's `05-tests.md` and `06-summary.md` — fs-native, the same write-back is a Bash heredoc, so ship holds no `Write`/`Edit`) |
| `lessons-consolidate` (standalone `_lessons.md` sweep) | Read, Grep, Glob, Edit, Write, Bash, TodoWrite — `Read`/`Grep`/`Glob` to parse and cluster entries, `Bash` for the size-cap measure (`grep -c '^## '`, `wc`) and the git-anchor checks (`git check-ignore`/`ls-files`), `Write`/`Edit` to rewrite the file only after diff approval; no `Task`, no MCP |
| `setup` (standalone project configuration dialogue) | Read, Write, Edit, Glob, Grep, Bash, TodoWrite, AskUserQuestion — `Read`/`Glob`/`Grep` read the existing `config.yaml`, the ticket folders, `.worktreeinclude` and the instruction files' commands sections; `Bash` runs the detection script (`skills/setup/scripts/detect.sh`), `git check-ignore`, `mkdir -p` for the ticket folders, and `mktemp -d` for the temp file a typed `.worktreeinclude` name is checked from — and, under `--check`, the `curl` of each declared test URL, `command -v jq`, and `git ls-files` over the `.worktreeinclude` patterns, each pattern read into a shell variable and written to its own temp file, and — when a test entry declares `driver` — `command -v node` and the installed browser driver's environment `doctor`; `Write`/`Edit` write `config.yaml`, `.worktreeinclude`, the `.gitignore` line and the `CLAUDE.md`/`AGENTS.md` `## Commands` snippet, each only after its diff is approved, and `Write` puts a typed name into a temp file so it never enters a command line; `TodoWrite` tracks the open questions; `AskUserQuestion` drives the dialogue + pipeline MCP tools (`ping`, the read-only connector check run before the storage-mode question — the one server call made before a mode is chosen, and none on a machine without the connector — and once as `--check`'s doctor round-trip for a server-native config; `pipeline_list_projects`, optional, listing the registry projects for the operator to pick the one to bind — a server without it degrades to the UUID prompt); no `Task`, no other MCP, and no ticket tools — setup writes nothing to the server |
| `guide` (standalone skill index) | Read — the body is static guidance; no `Task`, no `Write`/`Edit`, no `Bash`, no MCP — mutates nothing |
| `triage` (standalone advisory inbox classifier) | Read, Glob, Grep — `Read` loads the operator's optional repo-path override (`~/.claude/feature-triage/projects.yaml`), and `Read`/`Glob`/`Grep` give read-only repo context inside a resolved checkout (the registry path each pending entry carries, or its override), including its `claudedocs/tickets/**` + server MCP tools, mode-independent (`inbox_triage_pending` for the work list, `inbox_triage_assess` — the skill's only write — `inbox_list`/`inbox_get` for duplicates and related items, `pipeline_list_tickets`/`pipeline_get_ticket` for covering tickets); no `Write`/`Edit`/`Bash`/`Task`, no `TodoWrite`, and no inbox-mutating or ticket-creating tool — a scheduled run cannot answer a permission prompt, so the body also names each one as never called |

`Agent` and `Task` are both listed for flow, plan, build, review-stage, close-stage, and ship because Claude surfaces expose the native spawn operation under either name. The selected runtime maps the same operational budgets to Codex skill-file reads, `spawn_agent`, waits, and `followup_task`; Claude tool names and role frontmatter do not imply native Codex tool filtering. Available tools remain subject to the skill's operational boundaries: flow sequences, reviewers inspect, build implements, and the close stage closes.

If you need a tool not in this table, add it explicitly and document why.

## Agents

| Agent role | Tools | Rationale |
|---|---|---|
| Explorer (`code-explorer`) | Read-only set + Serena semantic tools | Describe, don't mutate; Serena adds symbol-level leverage |
| Analyst (`requirements-analyst`) | Read-only set | Describe, don't mutate; purely spec/analysis work — no codebase navigation |
| Reviewer (`code-reviewer`, `security-engineer`, `performance-engineer`) | Read-only set | Reviews must not mutate the tree; work on diffs, not codebase navigation |
| Architect (`code-architect`) | Read-only set + Serena semantic tools | Pattern comparison across sibling code is this agent's core work |
| UI tester (`ui-tester`) | Read tools + `Write`, `Edit`, `Bash` + Playwright/Chrome MCP | Browser testing — the one mutating agent in this table: `Write` codifies passing runs into spec files, `Bash` runs the test framework and `git check-ignore`s a storage-state path before saving it, and on a driver pass runs the injected browser driver's `drive`, `evidence` and `doctor` verbs — never `launch`, `cleanup` or `install`, which the pre-flight owns; `Edit` adjusts specs. `browser_set_storage_state`/`browser_storage_state` are additive-optional (version-gated — falls back to `attach_tab` when absent); `browser_resize` (Playwright) and `resize_page` (DevTools, for an `attach_tab` session) set the desktop and mobile widths every required-check capture is taken at — one resize tool per browser the tester can drive (`skills/build/references/ui-checks.md` §2 says how a missing tool is reported) |
| Finalizer (`finalizer`) | `Read`, `Glob`, `Grep`, `Bash`, `Write`, `Edit` + pipeline MCP tools (`pipeline_get_ticket`, `pipeline_list_tickets`, `pipeline_write_artifact`, `pipeline_transition_ticket`, `pipeline_update_ticket`) | The close stage's post-gate mechanics — the second mutating agent in this table, and the minimum budget for them: `Bash` runs every `git`/`gh` command (stage, commit, push, `gh pr create`, the fs-native folder move, worktree removal); `Write` creates the `git commit -F` message file; `Edit` makes the fs-native `status` frontmatter flip and appends PR linkage to `06-summary.md`; `Glob`/`Grep` serve the fs-native materialized-child scan behind the Epic-completion predicate; `Read` loads the three tail references. The MCP tools are the server-native equivalents of the same four writes. No `Agent`/`Task` — a leaf role that never delegates; no `TodoWrite`, `WebFetch` or `WebSearch` — it decides nothing and looks nothing up |

**Read-only set:** `Glob, Grep, LS, Read, NotebookRead, WebFetch, TodoWrite, WebSearch`. (`KillShell` and `BashOutput` are deliberately excluded — they only make sense paired with `Bash`, which read-only agents don't have.)

**Serena semantic tools** (optional enhancement — additive, agents fall back to Grep/Glob/Read when Serena MCP is unavailable): `mcp__serena__find_symbol`, `mcp__serena__find_referencing_symbols`, `mcp__serena__get_symbols_overview`. Added to agents whose core work is symbol-level navigation or cross-file pattern recognition. Not added to reviewers — they work on diffs, not codebase navigation, and the tools would be noise.

## verify plugin

The `verify` plugin ships three skills and no agents, under `plugins/verify/skills/`. A skill's `Bash` reaches the browser driver only as `node '<driver>' <verb> …`, a single-quoted absolute path to either the plugin's own `drivers/browser/cli.mjs` or the installed copy under `~/.feature-pipeline/verify/`; `map-check` holds no `Bash`.

| Skill | Typical budget |
|---|---|
| `setup` (user-only, `disable-model-invocation: true`) | Read, Write, Edit, Glob, Grep, Bash, AskUserQuestion — `Bash` installs and checks the browser driver and drives the two-step proof run, and runs `git check-ignore`; `Write`/`Edit` write the feature map and the `driver` and `feature_map` keys into the project's `test:` entry; `Read`/`Glob`/`Grep` read the repository the map is generated from; `AskUserQuestion` asks what the repository leaves open (on Codex, the same question is asked in plain text) |
| `run` (headless acceptance-criteria verification) | Read, Write, Glob, Grep, Bash + pipeline MCP tools (`pipeline_get_ticket`, `pipeline_get_artifact`, for a server-native ticket's criteria) — `Bash` runs `printenv HOME`, the installed driver and `git check-ignore` and nothing else; `Write` writes the run directory's entry and step files and each evidence home's `report.json`; no `Edit` — it never changes code, tickets, the feature map or config. The pipeline tools are dual-listed by hand: `scripts/check-tool-parity.sh` walks only `plugins/feature` |
| `map-check` (feature-map drift report) | Read, Glob, Grep — read-only: it writes nothing, runs no command and asks nothing |
